# 8. Crosscutting Concepts

System-wide rules and patterns that hold across building blocks. Each concept
states the problem, the approach, and where it is implemented — the
implementing blocks live in [§5](05-building-blocks.md), one-off decision
rationale in [§9](09-decisions.md) behind `(→ ADR-NNN)` pointers, and the
scenarios that exercise these concepts in [§6](06-runtime-view.md).

## 8.1 Behavior Tree Execution Model

**What:** All agent logic is expressed as behavior trees — hierarchical structures of Sequence, Selector, Action, Condition, ChainAction, and decorator nodes (→ ADR-001).

**Why:** BT nodes are composable, testable, and evolvable. The tick-based execution model supports multi-step planning with interleaved LLM calls. StrategyRouter + OutcomeSelector provide structured fallback.

**Where:** `internal/engine/tree.go` (BuildTree, RunTask, Blackboard), `internal/engine/registry.go` (action/condition registration), `internal/domains/` (tree definitions).

**Effect:** Every task flows through PreGate→StrategyRouter→OutcomeSelector. New capabilities are added by registering actions — no control flow changes needed.

**Non-terminal HITL outcome (2026-07-13, ADR-077):** `RunTask`'s tick loop and terminal `switch` recognize `bb.Outcome == "pending_approval"` (set by a `HumanApprovalGate`, `internal/engine/hitl_gate.go`) as a third case alongside success/failure: the loop stops ticking immediately instead of spinning to the 1000-tick `maxTicks` limit, and the outcome is preserved rather than collapsing to `"partial"`.

**Rate-limit carryover sentinel preserved too (2026-07-15, ADR-120):** The terminal `switch` gained a matching `case bb.Outcome == "goap_fusion_rate_limited"` (the Claude rate-limit carryover, [§6.4](06-runtime-view.md)/ADR-016), placed ahead of the `code`-keyed arms so it wins regardless of whether the tree's raw terminal `code` is `1` (an in-tree fallback such as `ScheduledAnalysisPath` completed) or `-1` (no fallback, or the fallback also failed). Until this landed, `RunTask` could silently overwrite the sentinel to a generic `"success"`/`"failure"` before it ever reached the scheduler-level consumers ADR-025/ADR-075 read it from.

**OutcomeSelector fallthrough made real (2026-07-13, ADR-084):** `MarkSuccessful` (`internal/engine/registry.go`) previously always returned `1`, so `OutcomeSelector`'s first child never failed and its `SelfCorrect`/`EscalateToDeepSeek` siblings were unreachable in production despite being fully implemented (`SelfCorrect`) or stubbed (`EscalateToDeepSeek`, which itself always returned `1` with no LLM call). `MarkSuccessful` now gates on the same `validateOutputQuality` check already used by the `ValidateOutput` condition (§8.7), returning `-1` on garbage/short output so the Selector actually falls through; `EscalateToDeepSeek` now mirrors `SelfCorrect`'s pattern — a real LLM call with an escalation-framed prompt, `bb.Result` written on success, `-1` on failure or no configured LLM. The `OutcomeSelector`'s three-child self-correction/escalation path is live for the first time.

## 8.2 ChainAction Nodes

**What:** LLM calls wrapped as behavior tree leaf nodes (→ ADR-006). The chain-type inventory — each type with its template variables — lives in [§5.5](05-building-blocks.md).

**Why:** Integrating LLM calls as BT nodes enables PreGate gating (don't call LLM if preconditions fail), retry wrapping, and StrategyRouter selection (try primary prompt, fall back to alternate prompt).

**Where:** `internal/engine/chains.go`. Config read from node `Name` (format: `chain_type:prompt_text`) and `Metadata` (max_tokens, temperature).

**Effect:** LLM integration is a first-class BT concept, not a side-effect. Chains can be retried, gated, and selected just like any other action.

**chain_type validated at authoring time (2026-07-16, ADR-130):** A ChainAction's `chain_type` (the segment before `:` in node `Name`, parsed by `parseChainConfig`) was previously checked only implicitly at tick time — `buildChainActionFn`'s dispatch `switch` falls through to a `default` case that sets `bb.Outcome = "chain_failed"` and returns failure, but only once the node actually runs. A new `IsKnownChainKind(kind string) bool` (`internal/engine/chains.go`), backed by a package-level `knownChainKinds` set covering every declared `ChainKind` constant, is now consulted by both validation entry points: `validateNode`'s `case "ChainAction":` (`internal/engine/validate.go`) and, since milestone 4/4, `walkValidate`'s `case "ChainAction":` (`internal/engine/verifier.go`) — each parses the node's `ChainConfig` the same way `buildNode` will and appends `<name>: unknown chain_type %q` (or, for `walkValidate`, `node %q: unknown chain_type %q`) to its own error list when the type doesn't match. A mistyped or unsupported `chain_type` now fails at tree-authoring/validation time through either `ValidateTree` or `ValidateTreeFull` instead of silently building a runnable node that only reveals the typo the first time it ticks. Pinned by `TestIsKnownChainKind` (`internal/engine/chains_test.go`), `TestValidateTree_ChainAction_UnknownChainType`/`_KnownChainType`/`_MixedTree` (`internal/engine/validate_test.go`), and `TestVerifierFull_ChainActionUnknownChainType`/`_KnownChainType` (`internal/engine/verifier_test.go`).

## 8.3 MCP Protocol Layer

**What:** All tools are exposed via JSON-RPC 2.0 over stdio, across the three MCP servers bt-agent, bt-evaluator, and bt-langagent (per-server tool inventories in [§3.2](03-context-scope.md); the bt-agent tool families in [§5.1](05-building-blocks.md)) (→ ADR-002).

**Why:** MCP provides a standardized interface between Hermes Agent and the Go BT platform. No custom protocols, no REST overhead. Stdio transport keeps it simple and gateway-managed.

**Where:** `internal/mcp/` (server implementation), `cmd/bt-agent/tools.go` (tool registration), `cmd/bt-agent/main.go` (server setup).

**Effect:** Hermes Agent sees the three servers' full tool surface ([§3.2](03-context-scope.md)). Adding a tool is a single `server.RegisterTool()` call. Gateway handles lifecycle (spawn, restart, health check).

**In-process seam:** `engine.Server` also exposes `HasTool(name) bool` and `Invoke(name, args) (*ToolResult, bool)` (`internal/engine/mcp_server.go`) so a registered tool can be asserted and driven by name in-process — without standing up the stdio JSON-RPC loop. This is a test/in-process seam only: it reads the private handler registry directly and deliberately bypasses the auth, rate-limit, sanitization, and tracing wrapping applied on the `tools/call` path, so it must never become a production request route.

**Registration-time Blackboard-locking primitive (2026-07-16, ADR-123 milestone 5/5):** `Server.RegisterBlackboardTool` (`internal/engine/mcp_server.go`) is a `RegisterTool` wrapper that runs the whole handler body under a new `Server`-wide `bbMu sync.Mutex`, so any tool sharing a `*Blackboard` across the concurrent `tools/call` goroutines `Run()` dispatches is synchronized by construction instead of relying on each handler author to remember an ad hoc lock. Proven by `TestServer_Run_MixedToolConcurrentCallsDoNotRaceOnSharedBlackboard` (`internal/engine/mcp_server_test.go`), which registers two distinct tools sharing one Blackboard, drives a mixed concurrent burst of both through the real `Run()` dispatch loop, and asserts clean `go test -race` output with no cross-call corruption. ~~`cmd/bt-agent` still uses its own, separate `mcpDeps.bbMu`/`lockBB()` mechanism (not this primitive) and has not migrated its tool registrations onto it — see ADR-123.~~ — resolved 2026-07-16 (ADR-124): `bt_run_task`, the four `bt_use_*_tree` switchers, `bt_delegate_to_tree`, `bt_blocks_compose`, and `bt_hitl_compose_task` all now register via `RegisterBlackboardTool`, and `mcpDeps` no longer carries a `bbMu` field or `lockBB`/`unlockBB` methods at all — this primitive is the only shared-blackboard lock left in the codebase.

## 8.4 File-Based Persistence

**What:** All state stored as JSON/YAML files with atomic writes (write .tmp → rename). No SQL database. (→ ADR-003)

**Why:** Git-friendly (diffs are readable), no database dependency, single-file atomicity prevents corruption. Simpler than SQL for a single-machine platform.

**Where:** `~/.go-bt-evolve/` directory tree ([§7.2.2](07-deployment.md)). Agent YAMLs, scheduler JSON, history JSON, reflection records, DLQ JSON, tree store JSON.

**Effect:** State survives restarts. Git can version agent definitions. Manual inspection and repair is possible with any text editor.

**Scoped-blackboard scope-ID normalization (cross-tool contract):** The persisted blackboard key-space is addressed by `blackboard.Scope{Kind, ID}`, and two independent surfaces construct that scope from user input: the daemon's MCP blackboard tools via `parseBBScope` (`cmd/bt-agent/blackboard_tools.go`) and the CLI inspector via `parseBBScopeFlag` (`cmd/bt-agent-cli/bb.go`). Both must normalize identically — each trims whitespace from the scope ID before building the scope — otherwise an entry persisted under a daemon-normalized scope becomes unreadable when the CLI is given a padded `--id`. The contract is pinned by `cmd/bt-agent-cli/bb_test.go`: a table-driven test over all three scope kinds plus a round-trip test that writes through a daemon-parsed scope and reads back through the CLI parse path, using the `bbManagerAt(dir)` construction seam so the production manager-setup path runs against a temp directory. The reflection feedback identifiers follow the same canonicalize-once contract: `recordUserFeedback` (`cmd/bt-agent/feedback_tools.go`) trims `user` and `treeID` once at entry and uses the trimmed values throughout — the stored record, the per-user workspace slug, and the cumulative `FilterByTreeNameStrict` satisfaction tally — where it previously validated on the trimmed value but stored the raw one, so a trailing-space tree id created records no later strict lookup could ever match (pinned by `TestRecordUserFeedback_TrimsUserAndTreeID`).

**Scoped-blackboard key normalization (`scopedStore`, 2026-07-15, ADR-092):** Below the scope-ID contract above, `blackboard.scopedStore` (`internal/blackboard/memory_store.go`) addresses entries within a scope by a `normalizeKey`-canonicalized key (trims whitespace, trims surrounding `/`, strips `..`). `set`, `delete`, `list`, and `listRecent` all normalized their key/prefix argument before touching `entries`, but `get` did not — a key written through `bt_bb_write` with leading/trailing whitespace or slashes was stored under its normalized form, yet `bt_bb_read` given that same raw key looked it up unnormalized and reported it missing, even though `set`→`get` is meant to round-trip. `get` now normalizes its key the same way, closing the one asymmetric path. Pinned by `TestBTBBWriteThenReadNormalizesKeyIdentically` (`cmd/bt-agent/blackboard_tools_test.go`), part of a characterization-test pass that also covers `blackboard_tools.go`'s other exported behavior.

**Per-user workspace path-segment safety:** Every per-user file lives under `users/<id>/…`, and `persona.SanitizeUserID` (`internal/persona/profile.go`) is the single boundary that turns an externally supplied user identifier into that directory name — the daemon's persona store resolves every workspace lookup through it (profiles, goal queues, automation ledgers, user-attributed generated-tree persistence via `persistGeneratedTreeForUser`), and autopilot derives its `auto-<user>-<sig>` agent names from it. The sanitizer allowlists `[A-Za-z0-9.-]`, maps every other rune to `_`, and returns `_anonymous` for empty input; because `.` is allowlisted, it additionally prefixes any all-dot result with `_` — a bare `"."` would otherwise resolve to the users root itself and `".."` to its parent when joined as a workspace path segment, turning a hostile user ID into a directory-traversal primitive against `~/.go-bt-evolve`. The contract is pinned by the adversarial-ID table in `internal/persona/persona_test.go` (`TestSanitizeUserID_AdversarialIDs`), which also asserts that no sanitized ID survives as `.`/`..` or contains a path separator.

**User-scoped runtime-generated tree resolution (2026-07-13, ADR-067/ADR-069, "Harden the ADR-133 personalization layer" program milestones 3/5 and 5/5):** The runtime-generated-tree fallback `agentexec.resolveUserTree` resolves a deterministic slug ID like `goal:automate_<slug>` by scanning every `users/<id>/trees` workspace in *sorted* order and returning the first hit — so two different users who each independently compile a personal tree under the same slug-derived ID collide, and the alphabetically-earlier user's tree silently satisfies the other's request (bob asking for his automation could receive alice's). `agentexec.ResolveGeneratedTreeForUser(user, id)` and its `domains.ResolveTreeIDForUser(user, id)` counterpart are the scoped fix: the shared reflections dir is still consulted first, but the per-user fallback loads only `users/<user>/trees` — never the cross-user scan. `domains.DynamicResolveForUserFn` is the injection seam `agentexec.init` wires to `ResolveGeneratedTreeForUser` alongside the existing unscoped `DynamicResolveFn`, and `resolveTreeIDWithResolver` factors `resolveTreeID`'s ID-prefix branching so the scoped and unscoped entry points share one implementation instead of drifting. Pinned by `TestResolveGeneratedTreeForUser_TwoUserCollision` and `TestResolveTreeIDForUser_ScopesToRequestingUser` (`internal/agentexec/wiring_test.go`), which save colliding same-ID trees for two users and assert each resolves their own. **Reachable from production since ADR-069:** `agent.RunDeps` gains a `ResolveTreeForUser UserTreeResolver` field alongside the unscoped `ResolveTree`, and `RunOnce` routes through it — instead of `ResolveTree` — whenever the resolved agent's `Definition.Metadata["user"]` is non-empty; both production wiring sites (`cmd/bt-agent/main.go`'s `resolveTreeForUser`, `internal/agentexec/deps.go`'s `NewRunDeps()`) now populate it from `domains.ResolveTreeIDForUser`, so the live `goal:automate_*` request path is protected end to end. Pinned by `TestRunOnce_UsesUserScopedResolverWhenAgentHasOwner` (`internal/agent/runner_test.go`).

**Knowledge-graph feedback (wired via the scheduler lifecycle):** The knowledge graph's runtime feedback — the RecordRun-mutated fields (Fitness, RunCount, EvolvedCount, LastOutcome, LastDuration, and — since 2026-07-15, ADR-105 — RecentRuns) and `uses_tool` edges — is in-memory and would otherwise be lost on restart. (`EvolvedCount` counts synthetic evolution write-backs separately from genuine executions; the evolved elite's `StructuralFitness` itself is held in-memory only and re-derived by evolution, not snapshotted — see ADR-028.) `internal/knowledge/feedback_persist.go` adds a same-pattern (atomic write .tmp → rename) JSON snapshot: `SaveFeedback`/`LoadFeedback` serialize only the feedback subset (static tree metadata is excluded, and Load merges into already-registered trees rather than clobbering them), and a debounced `FlushFeedback(force)` — driven by `MarkFeedbackDirty` and a min-interval throttle — avoids rewriting the whole graph on every bursty RecordRun. The writer takes no `internal/agent` dependency. The `internal/agent` scheduler now drives that lifecycle end to end. `SchedulerConfig` carries an optional `FeedbackPath` (and `FeedbackFlushInterval`, defaulting to 30s when zero); when the path is set, `NewScheduler` re-hydrates prior feedback with `LoadFeedback` (logging, not failing, on error — matching the missing-file-no-error contract) and arms the debounced writer via `ConfigureFeedbackPersistence`. Both `RecordRun` call sites (`RunNow` and the scheduled `runJob`) then call `persistRunFeedback`, which marks the graph dirty and attempts a throttled best-effort `FlushFeedback(false)`; `Stop()` issues a forced `FlushFeedback(true)` so feedback pending inside the throttle window is durably written on shutdown. `ConfigureFeedbackPersistence` resets the throttle clock on each arming so a re-armed process-global `GlobalGraph` always flushes on its first dirty mark. Together this closes the learn→evolve loop across restarts: a fresh process reads back the accumulated Fitness/RunCount/tool-edges instead of resetting them. The production daemon supplies that path: `cmd/bt-agent/main.go` factors the whole `SchedulerConfig` assembly out of `main()` into a `buildSchedulerConfig(cfg, reg, hist)` helper, which sets `SchedulerConfig.FeedbackPath` to `agent.FeedbackFile()` — `~/.go-bt-evolve/feedback.json`, the single canonical snapshot location, resolved through the package-level `feedbackSnapshotPath()` helper — alongside the durable `FileJobStore` and per-agent circuit-breaker store. Extracting the helper lets `wiring_test.go` assert the assembled config end-to-end (`TestDaemonSchedulerConfigWiresFeedbackPath`) rather than only checking the `feedbackSnapshotPath()` helper in isolation, so a regression that drops the `FeedbackPath` line — silently disabling persistence — now fails a test instead of shipping dormant.

**Domain-aware fitness override for genuine runs (2026-07-15, ADR-097):** RecordRun's generic runtime-success EMA above is a coarse success/failure signal that cannot tell an honestly-scored NotebookLM run from one padded with fabricated claims. `KnowledgeGraph.RegisterDomainFitness(treeID string, fn func(runs []RunSummary) float64)` (`internal/knowledge/graph.go`) is the injection hook: a genuine-execution `RecordRun` call now always appends `{Outcome, Quality}` to a bounded `TreeMeta.RecentRuns` window (`maxRunHistory` = 20, oldest evicted first), and when a function is registered for `rec.TreeID`, `Fitness` is set to `fn(tree.RecentRuns) * 100` in place of the 0.9/0.1 EMA — trees with no registration are unaffected. `domains.RegisterNotebookLMFitness(kg)` (`internal/domains/notebooklm_fitness.go`) is the first caller: it registers the existing `NotebookLMFitness` anti-fabrication-and-quality scoring function — previously computed but never invoked by any production path — for both `"notebooklm"` and `"notebooklm_consumer"` tree IDs, converting each `RunSummary` to its own `NotebookLMRunSummary` shape. `cmd/bt-agent/main.go` calls it once at startup, immediately after `kg.ExpectedDomains` is seeded. ~~⚠️ `RecentRuns` is not part of the `feedback_persist.go` snapshot above (only `Fitness`/`RunCount`/`EvolvedCount`/`LastOutcome`/`LastDuration` are, per ADR-028) — a daemon restart keeps the last computed `Fitness` but resets the run-history window to empty, so the domain function only ever scores genuine runs recorded since the most recent restart.~~ — resolved 2026-07-15 (ADR-105): `treeFeedback` (`internal/knowledge/feedback_persist.go`) now also carries `RecentRuns`, and `SaveFeedback`/`LoadFeedback` snapshot/restore it alongside the other feedback fields, so a restart restores the full run-history window a registered domain fitness function scores from instead of resetting it to empty. The `domainFitness` registrations themselves are still equally in-process-only and must be re-established by `RegisterNotebookLMFitness` on every startup. Pinned by `TestRecordRun_DomainFitness_OverridesGenericEMA`, `TestRecordRun_TracksBoundedRecentRunsWindow`, `TestRecordRun_NoDomainFitness_KeepsGenericEMA` (`internal/knowledge/graph_test.go`) and `TestRegisterNotebookLMFitness_WiresIntoKnowledgeGraph`/`TestRegisterNotebookLMFitness_DoesNotAffectOtherTrees` (`internal/domains/notebooklm_fitness_wiring_test.go`); the persistence fix itself is pinned by `TestSaveLoadFeedback_RecentRunsRoundTrip` (`internal/knowledge/feedback_persist_test.go`).

**Shared-file DLQ persistence (2026-07-10, ADR-036):** `dead_letter_queue.json` is a *multi-writer* file — the daemon, the dashboard, and MCP siblings each hold an independent `DeadLetterQueue` over it — and its persistence now actually honors the contracts this section claims (its `save()` was the one remaining blind `os.WriteFile`). `save()` (`internal/reliability/reliability.go`) writes via the ADR-003 tmp+rename idiom, and `load()` no longer discards the `json.Unmarshal` error: a corrupt file is quarantined to `<path>.corrupt`, so the queue restarts empty but the next save can no longer persist the wipe over the only copy of the dead-lettered tasks, and the evidence survives for forensics. Because a whole-file rewrite from a stale view would erase a sibling's `Requeue` stamp, every save first re-merges the on-disk entries under an exclusive advisory flock on the `<path>.lock` sidecar (`acquireFileLock` — a local replication of the ADR-024 idiom, since `internal/reliability` imports zero internal packages; this unlink-on-release variant re-verifies the sidecar inode after acquisition and retries on the live path). The merge is per-entry and monotonic: a strictly higher on-disk `Attempts` marks the disk write as newer and its `Attempts` + `RequeuedAt` are adopted together (equal `Attempts` keeps memory, preserving `Replay`'s deliberate post-failure clear of `RequeuedAt`), and `Abandoned` merges as OR so a stale save can never resurrect a poison pill into the auto-requeue pool. Membership stays memory-authoritative — `Replay` removals and `Purge` stick; disk-only entries are not adopted by a save (new-entry visibility comes from `Reload`, §8.6). A lock failure degrades to the merged-but-unserialized write rather than dropping the save. Pinned by `TestDeadLetterQueue_SaveAtomicReplace`, `TestDeadLetterQueue_LoadQuarantinesCorruptFile`, and the two-queue shared-file clobber regressions `TestDeadLetterQueue_SaveMergesSiblingRequeueStamps` / `TestDeadLetterQueue_SaveMergesSiblingAbandoned` (`internal/reliability/reliability_test.go`).

**Dashboard task-store atomicity and fail-loud corruption handling (2026-07-15, ADR-101):** `dashboard.TaskStore` (`internal/dashboard/tasks.go`) was the one persisted store in this section that did not actually follow the atomic-write idiom `8.4`'s own **What** line claims: `Save` called `os.WriteFile(s.path, ...)` directly (truncating the live file in place before the new content was fully written), and `Load` discarded `json.Unmarshal`'s error via `_ = json.Unmarshal(data, s)` — a corrupted `tasks.json` was indistinguishable from a fresh, empty store, so every previously persisted task silently vanished. `Load` now returns a parse/read error to its caller (a missing file remains the historical no-op "fresh store" case), `NewTaskStore` — the constructor `cmd/bt-dashboard/main.go` actually calls at startup — panics on that error instead of swallowing it, and `saveLocked` writes through a sibling `<path>.tmp` file and renames it into place, mirroring `QTable.Save`/`IslandModel.Save` and the DLQ's own `save()` above. Pinned by `TestTaskStore_LoadReturnsErrorOnCorruptJSON`, `TestNewTaskStore_PanicsOnCorruptFile`, and `TestTaskStore_SaveAtomicWriteLeavesOriginalIntactOnFailure` (`internal/dashboard/tasks_test.go`), the last of which chmods the store's directory read-only to force the temp-file creation to fail and asserts the original `tasks.json` content is untouched.

## 8.5 Evolution Pipeline

**What:** Common pattern for tree improvement: evaluate → order mutations → apply top mutation → re-evaluate → compare fitness → accept (commit) or rollback.

**Why:** Multiple algorithms (Stockfish, Pareto, MAP-Elites, Island, Q-Learning, Expert) share this pattern. A unified pipeline reduces duplication and ensures consistent safety checks.

**Where:** `internal/evolution/` — each algorithm file, `internal/gardener/` (evolution_v2.go for cycle orchestration).

**Effect:** Evolution is auditable (git commits), reversible (rollback), and measurable (fitness delta tracking).

**Experience-grounded memory (ADR-017):** The genetic path additionally learns across runs. `Population.EvolveWithExperience` (`internal/evolution/learning.go`) warm-starts operator selection from the persistent `ExperienceBank` — the top-5 `RetrieveByTreeType` hints for the population's tree type bias 50% of mutations toward operators that previously improved fitness on similar trees — and records every fitness-improving mutation back via `AddFromMutation` (regressions are discarded, so the bank only accumulates successes). A nil bank degrades to plain `Evolve`. The daemon constructs one bank at startup (`~/.go-bt-evolve/experience/experience.json`, honoring `BT_AGENT_HOME`) and plumbs it through `mcpDeps` into `bt_evolve_genetic` and `bt_evolve_bottlenecks`, so mutation experience compounds across restarts the same way knowledge-graph feedback does (§8.4). The bank is bounded at 500 entries (`experienceBankCap`) with quality-aware eviction — lowest `QualityScore` first, oldest first among equal quality, entries with `TimesReused >= 3` evicted only after every less-proven entry is gone — enforced on every `Add` and, for oversized legacy files, on load in `NewExperienceBank` (ADR-018). Since 2026-07-15 (ADR-109), `EvolveWithExperience` is a thin wrapper over a more general `Population.EvolveWithExperienceContext(generations, fitnessFn, bank, query)`: an empty `query` keeps the tree-type warm-start above verbatim, while a non-empty one warm-starts from `bank.Retrieve(query, experienceHintTopK)` instead — `Retrieve`'s Jaccard-similarity ranking is not filtered by tree type, so a query built from a concrete failing task can surface relevant prior mutations recorded under a different tree type entirely.

**Gardener adoption (ADR-021):** The same bank now also feeds the 24/7 gardener cycle. `gardener.Config` carries an optional `*evolution.ExperienceBank`; when set, `evolveTreeV2` (`internal/gardener/evolve_v2.go`) records every *accepted* mutation via `AddFromMutation` with its per-candidate composite delta, and `biasCandidatesWithExperience` reorders the `evaluator.OrderMutations` heuristic ranking before candidates are tried — the top-5 `RetrieveExperienceHints` for the tree type (quality ≥ 0.5) boost matching op/target candidates by 0.15 × quality under a stable sort, and matched entries are `MarkReused`. Since 2026-07-16 (ADR-125), both the record and retrieve sides additionally condition on `lastFailureTask(records)` — the tree's most recent `evolution.Failure` reflection record's `Task` text: a non-empty value is threaded into `AddFromMutation`'s `failureContext` argument (tagging the recorded entry's `Context` with `failing_task=<text>`) and into `biasCandidatesWithExperience`'s new `query` parameter, which routes retrieval through `bank.Retrieve(query, experienceBiasTopK)` — not filtered by tree type — instead of `RetrieveExperienceHints`; an empty task (no failing record yet) leaves both sides exactly as described above. `cmd/bt-gardener` constructs the bank at `agent.HomeDir()/experience` — deliberately the daemon's directory — so gardener and bt-agent accumulate mutation experience into one shared store. A nil bank degrades to the historical no-recording, heuristic-order-only behavior. Because both binaries rewrite the whole `experience.json` on every `Add`, `addEntry` first re-merges the on-disk entries by ID (adopting entries only on disk, keeping the higher `TimesReused` on conflicts) before appending and persisting, so concurrent daemon and gardener writers no longer clobber each other's recent entries (ADR-022); the merged set still passes the ADR-018 cap enforcement. The merge→rename window itself is serialized cross-process by an exclusive advisory flock on the `experience.json.lock` sidecar (`acquireExperienceLock`, `internal/evolution/file_lock.go`), held from the disk merge until the atomic rename completes, and every full-file write path — `addEntry`, `MarkReused`, and the exported `Persist()` — runs the same lock→merge→write sequence through a shared `persistLocked` helper, so no exported path can rewrite the file from stale memory; if the lock cannot be acquired (e.g. read-only directory), the write degrades to the unlocked merged path rather than dropping the entry (ADR-024).

**Within-run reinforcement (ADR-019), now cross-run durable and bounded (ADR-041):** Complementing the cross-run ExperienceBank, `Population.EvolveQLearning` (`internal/evolution/learning.go`) learns *within* a single evolution run: each offspring mutation's category is chosen epsilon-greedily from a `QTable` keyed by the child's structural state, and the fitness delta is fed back via `Update` — regressions are discarded by the same quality-gate pattern but still recorded, so the table learns which categories to avoid per state. The table itself is no longer discarded with the response: `QTable.Save`/`Load` persist `Values` as JSON — atomic tmp+rename under the same ADR-024 `acquireExperienceLock` flock the ExperienceBank uses, merging state-by-action on load so values not present on disk survive, a missing archive a silent cold start and a corrupt one an error that leaves memory untouched — and `bt_evolve_qlearning` (`cmd/bt-agent/tools.go`) warm-starts from and re-persists to a per-base-tree `~/.go-bt-evolve/qtable_archive-<tree>.json` (`qtableArchivePath(treeID)`, sanitized the same way as `islandArchivePath` — ADR-034), reporting `warm_started` plus `learned_states_before`/`learned_states_after` so a caller can see learning resume rather than restart. `QTable` also gains an optional `Cap` (0 = unbounded) enforced on `Update` by evicting the least-recently-updated state first, tracked in a cumulative `EvictedStates` counter; `bt_evolve_qlearning` sets it via an optional `state_cap` request parameter (default `population*10`, mirroring the island archive's `population_cap`/`island_cap` — ADR-040) set on the table *before* `Load`, and reports the resulting `evicted_states`. Since 2026-07-15 (ADR-111), the `qt.Save`/`ek.Save` pair is itself gated: `benchmarkGateEvolvedWinner` runs `EvolveQLearning`'s returned `best` and the base tree through the tree's real `internal/benchmark` suite and skips both saves — reporting `benchmark_gate_rejected`/`benchmark_base_success_rate`/`benchmark_winner_success_rate` — when the winner's measured success rate regresses, rather than trusting structural fitness alone. `Population.MemeticEvolve` (`internal/evolution/local_search.go`) instead refines offspring with a pluggable `LocalSearcher` (hill-climb, simulated annealing, or tabu), and has no analogous durable state. **Persisting the evolved winner, not just its fitness (ADR-042):** `Population.EvolveWithExperience` — the bank-warm-started genetic algorithm `bt_evolve_genetic`, `bt_evolve_bottlenecks`'s genetic-fallback branch, and `bt_evolve_selection_pressure` all drive — now returns its winning `*evolution.SerializableNode` instead of discarding it after `BestFitness` is read off. `persistEvolvedWinner(deps, baseTreeID, winner, fitness, result)` (`cmd/bt-agent/tools.go`) persists it under a derived `"<baseTreeID>-evolved"` id through the same `persistGeneratedTree` seam every other MCP-generated tree uses (`engine.ValidateTreeFull` gate, `treeStore.SaveNamed`), then calls `KnowledgeGraph.RegisterEvolved(baseID, evolvedID, nodeCount, fitness)` (`internal/knowledge/graph.go`) to create-or-update the evolved tree's KG entry — inheriting the base tree's category/capabilities/keywords on first sight, folding `fitness` into `StructuralFitness` via the existing monotone-and-clamped `evolvedFitness` helper (ADR-028), and connecting `baseID → evolvedID` via an `evolved_from` edge so `DiscoverRelated` surfaces it. All three tools report the persisted id as `evolved_tree_id`. `bt_evolve_qd` and `bt_evolve_island` are unaffected — they still write back fitness only (ADR-026), not a tree-store entry. Since 2026-07-13 (ADR-078), the overwrite itself is fitness-gated: `RegisterEvolved`'s `NodeCount`/`EvolvedCount`/`StructuralFitness` bookkeeping only updates when the new fitness beats what is already stored for `evolvedID`. Since 2026-07-13 (ADR-083), that gate and the disk write are ordered atomically: a new non-mutating `KnowledgeGraph.EvolvedFitnessImproves(evolvedID, fitness)` peek decides whether to attempt `persistGeneratedTree` at all, and `RegisterEvolved` itself now runs only *after* `persistGeneratedTree` reports `persisted: true` — so a validation failure or a `nil` `deps.treeStore` can no longer leave the knowledge graph's fitness/node-count bumped to a winner with no backing tree-store file. Since 2026-07-15 (ADR-118), the same seam closes the two remaining production evolve tools that computed a winner and threw it away: `bt_evolve_memetic` now passes `Population.MemeticEvolve`'s returned winner (previously consulted only for `CountNodes`/`BestFitness`) to `persistEvolvedWinner`, and `bt_evolve_bottlenecks`'s CMA-ES branch does the same with `TuneTreeParameters`'s tuned `*SerializableNode` (previously bound to `_` and dropped) — see ADR-020 below for that branch specifically. Since 2026-07-16 (ADR-126), a typed `KnowledgeGraph.EvolutionLineage(treeID) (baseID string, evolvedIDs []string, ok bool)` (`internal/knowledge/graph.go`) gives external callers the same `evolved_from`-edge walk `DiscoverRelated` already does, but as a direct base↔descendants lookup instead of a fuzzy discovery match: called with a base tree's ID it returns every evolved descendant, called with any descendant's ID it returns the shared base plus every sibling descendant, and `ok=false` when `treeID` has no evolution lineage at all. `cmd/bt-dashboard/main.go`'s `handleTrees` and `handleMetricsLive` are its first production callers ([§5.4](05-building-blocks.md)), surfacing lineage the `/api/trees` response had never exposed despite `RegisterEvolved`/`DiscoverRelated` maintaining it since ADR-042.

**Consulting lineage before spending another evolution budget (2026-07-16, ADR-127):** `EvolutionLineage` gained its first re-evolution-gating consumer, closing milestone 4/4 of the same program ADR-126 began. `KnowledgeGraph.EvolutionLineageBestFitness(treeID) (fitness float64, ok bool)` (`internal/knowledge/graph.go`) resolves `treeID`'s lineage and returns the highest `StructuralFitness` among its own evolved descendants (`ok=false` when `treeID` has none of its own, including when `treeID` is itself the evolved side of some other base). A new `lineageSkipsReEvolution(kg, treeID, baseFitness)` helper (`cmd/bt-agent/tools.go`) combines that with the tree's shared `TrackRecord` archive at `trackRecordArchivePath(treeID)` — the same per-tree archive `bt_evolve_qd`/`bt_evolve_multiobjective`/`bt_evolve_pareto`/`bt_evolve_qlearning`/`bt_evolve_island` already record benchmark-gate accept/reject outcomes to (ADR-119): it reports true only when a descendant's fitness beats `baseFitness` (the bottleneck's runtime `SuccessRate`) *and* that archive's `WinRate() >= 0.5` — a history with more benchmark-gate rejections than acceptances means the stored evolved winner may no longer be trustworthy, so re-evolution proceeds instead of deferring to a possibly-stale lineage. `bt_evolve_bottlenecks`' per-bottleneck loop (`cmd/bt-agent/tools.go`) calls this right after the existing baseTree-resolution check and before either the CMA-ES or genetic branch runs; a skipped tree is appended to a new `lineage_skipped` result list — mirroring the pre-existing `skipped` list for unresolvable trees — instead of silently dropping out of `report`, and earns no `algorithms` tally entry.

**Parameter tuning vs structural mutation (ADR-020):** Not every underperforming tree needs new topology — some just need better numbers. `TuneTreeParameters` (`internal/evolution/cmaes.go`) is the single Extract→Optimize→Apply seam: `ExtractParameters` collects `TunableParam`s from both `Metadata` keys and the `TimeoutMs`/`MaxRetries` struct fields (seeding `InitValue` from the live field value), `CMAESOptimizer.Optimize` searches normalized [0,1] space with an adapter that denormalizes each candidate onto a scratch clone, and the winner is applied to a fresh clone — the input tree is never mutated, and `ok=false` is returned without any fitness calls when no parameters exist. `bt_evolve_bottlenecks` routes on that flag: trees with tunable parameters get CMA-ES tuning (`"algorithm":"cmaes"`), parameterless trees fall back to structural evolution (`"algorithm":"genetic"`), and the report's top-level `algorithms` tally shows the split. Since 2026-07-15 (ADR-118), the CMA-ES branch persists its tuned winner too: `TuneTreeParameters`'s returned tuned tree — previously bound to `_` and discarded, leaving only `bestFitness` in the report entry — is now passed to `persistEvolvedWinner` (§8.5 ADR-042) the same way the genetic branch's winner already was, so a `cmaes`-routed and a `genetic`-routed report entry are no longer asymmetric in whether their winner survives to the tree store.

**Conditioning the bottleneck warm-start on the failing task's semantics (2026-07-15, ADR-109):** The genetic-fallback branch above now calls the new `EvolveWithExperienceContext` (§8.5 ADR-017) instead of plain `EvolveWithExperience` — `bt_evolve_genetic` and `bt_evolve_selection_pressure` still call the plain form. **Durable Selector-ordering telemetry (ADR-029):** The deterministic Selector-child-ordering optimizers gain the same restart-durable, merge-safe persistence the ExperienceBank uses. `SelectorOptimizer.SaveSelectorStats`/`LoadSelectorStats` (`internal/evolution/selector_optimizer.go`) and `DTAnalyzer.Save`/`Load` (`internal/evolution/decision_tree.go`) both write JSON via tmp + rename under the ADR-024 `acquireExperienceLock` sidecar flock, and both *merge on load* rather than clobber — summing each `ChildStats`' success/failure/running/tick counts (and each `DTSelectorStats` path's `HitCount`/`SuccessCount`/`TotalTasks`) so per-Selector telemetry from independent writers and earlier runs accumulates. A missing file is a silent no-op; `SaveSelectorStats` re-merges the on-disk snapshot into memory before rewriting, and an in-process `sync.Mutex` keeps that merge atomic against the rewrite. Empty telemetry is handled loud-free: `BTOptimizer.OptimizeSelectors` (and `BestSplitCondition`) degrade to a no-op instead of shuffling paths on absent information-gain scores. Feeding real outcomes into that store is `knowledge.RecordSelectorOutcomes(trace, path)` (`internal/knowledge/traces.go`): it walks an executed `DecisionTrace`, notes every `NodeType=="Selector"` step, and for each child step attributed to a Selector via the new `TraceStep.ParentName` field records that child's success/failure into a fresh `SelectorOptimizer`, then persists via the accumulating `SaveSelectorStats`. **Applying the telemetry (milestones 4–5 of 5):** `SelectorOptimizer.ApplyLearnedOrdering(tree)` (`selector_optimizer.go`) is the apply primitive — it walks a tree and reorders every Selector's children by their learned rank (`OrderChildren`), while `isSelectorFallback` keeps fallback/default-path children and `AlwaysSucceed` leaves last so the node's short-circuit semantics survive (the default path is never promoted just because it "succeeds" every tick, honoring the `isDefaultPath` guard in `decision_tree.go`). **Feeding `ExplainLastFailure` a real path (2026-07-13, ADR-058):** The two production `DecisionTrace` record sites (`internal/agent/scheduler.go`'s `RunNow` and `runJob`) previously recorded traces with `Steps` always empty, so `KnowledgeGraph.ExplainLastFailure` (exposed as the `bt_kg_explain` MCP tool) rendered a bare `Path:` header with nothing under it. `RunResult` (`internal/agent/runner.go`) now carries the run's terminal child ticks (`ChildTicks: bb.ChildTicks()`), and both scheduler sites convert them via a new `stepsFromChildTicks`/`knowledge.StepsFromChildTicks` bridge (`ChildTick{Parent,Child,Status}` → `TraceStep{NodeName,ParentName,Status}`, skipping ticks with an empty `Child`) before calling `Record`, so `ExplainLastFailure` now renders a genuine, non-empty path for every terminated run. **Proactive crisis intervention in the GA loop (ADR-031):** `Population.Evolve` (`internal/evolution/learning.go`) no longer converges silently into a death spiral. Each generation it reuses the `PopulationState` already built for the LLM supervisor and passes it to the lazily-initialized `Population.Crisis *CrisisDetector`'s `DetectPopulation`, recording the returned reasons (`diversity_collapse`/`regression_spiral`/`quality_crash`) on `Population.CrisisReasons` in first-seen order across generations. When a crisis fires — or the supervisor itself flags `PhaseCrisisIntervention` (`guidance.Intervention`, previously computed and discarded) — that generation's mutation rate is overridden with `CrisisDetector.GetEmergencyMutationRate()` (μ_emergency = 0.50) and, once a streak-based spiral (`regression_spiral`/`quality_crash`) completes its emergency generation, `ResetPopulation()` clears the streak counters so the recovered population isn't immediately re-flagged by stale history (a pure `diversity_collapse` leaves the streaks intact so a still-regressing population keeps accumulating toward the spiral threshold). The applied rate is exposed on `Population.LastMutationRate` so callers can observe whether a generation ran under emergency control. This is reachable in production through `bt_evolve_qd` — since 2026-07-15 (ADR-110) the tool constructs a `MAPElitesPopulation` and drives `EvolveMAPElites` directly instead of plain `Evolve`, so its crisis intervention now runs through the LLM-supervised path described below rather than the bare-GA path — and, since ADR-038 milestone 2, through `bt_evolve_genetic`/`bt_evolve_bottlenecks`/`bt_evolve_selection_pressure` too, whose live-experience-bank path runs the same envelope via the extracted `selfHealGeneration` helper shared with `Evolve` (`EvolveQLearning` and `MemeticEvolve` ran outside it until 2026-07-15, ADR-121, below). Milestones 4–5 close the recovery loop: a nil-safe `Specialists *SpecialistRegistry` on `Population` (and, via embedding, `MAPElitesPopulation`) receives the top-`eliteCount` validated elites through `Observe` every generation, and an emergency generation calls `resurrectExtinctSpecialists`, which replaces the weakest non-elite individual with a `Resurrect`'d archetype for each niche flagged by `ExtinctSpecialists` (absent ≥ 5 generations, fitness ≥ 0.5). Milestone 5 also folds the full `DetectPopulation` → emergency-rate → `ResetPopulation` intervention into the LLM-supervised `EvolveMAPElites`, which had built the grid-aware `PopulationState` and called `Guide` but discarded every crisis signal. The archive/resurrect half is live in production: `newProductionPopulation` (`cmd/bt-agent/tools.go`) seeds every MCP-tool population's `Specialists` via `SeedSpecialistRegistry`, so `Observe`/resurrection actually run wherever `selfHealGeneration` does — now including `EvolveWithExperience`'s live-bank path (ADR-038). ADR-038 milestones 4–5 extend the same envelope to `ParetoPopulation.EvolvePareto` (`pareto.go`, which embeds `*Population` and scalarizes `MultiFitness` via `CompositeScore` for the crisis check) and `IslandModel.EvolveAll` (`island.go`, one `selfHealGeneration` call per island, seeding `Specialists`/`Crisis` for islands added via the bare `AddIsland` path so none can skip the envelope for lack of a registry): the island half is live in production through `bt_evolve_island` (whose islands are already `SeedSpecialistRegistry`-seeded); since ADR-057, the Pareto half is too — `EvolvePareto` gains a production caller in the deterministic `bt_evolve_pareto` MCP tool, built via the same `newProductionPopulation` helper (so `Specialists` arrives pre-seeded, matching its sibling evolve tools) and surfacing `Population.HealthSnapshot()` under `health` from its first release, since `EvolvePareto` already ran inside `selfHealGeneration` before it ever had a caller. ADR-051 closes the one remaining production Evolve variant that had shipped with no self-healing at all: `NSGAIIPopulation.Evolve` (`multi_objective.go`) now runs the same `selfHealGeneration` envelope, `NewNSGAIIPopulation` seeds a nil-safe `Specialists` registry the same way `IslandModel`'s `AddIsland` path does, and `bt_evolve_multiobjective` overwrites that empty default with a `SeedSpecialistRegistry`-loaded one and surfaces `Population.HealthSnapshot()` under a `health` key — bringing every `bt_evolve_*` GA/multi-objective/island tool except `bt_evolve_qlearning` and `bt_evolve_memetic` onto the shared envelope at that time. **Calibrated crisis mutation budget in the gardener cycle (2026-07-15, ADR-102):** The GA-level crisis intervention above is a separate mechanism from the gardener's own per-cycle "Stage 3.5" crisis check: `evolveTreeV2` (`internal/gardener/evolve_v2.go`) keeps its own `*evolution.CrisisDetector` on `gardener.Config.CrisisDetector` and, on a `Detect` hit, calls `Intervene` to boost that cycle's mutation budget — but until this ADR it discarded the returned `InterveneAction.EmergencyRate` entirely and always set `maxMutations = g.cfg.MaxMutations * 2`, a hardcoded doubling that ignored the detector's own calibrated μ_emergency value. `maxMutations` is now `ceil(g.cfg.MaxMutations / (1 - rate))` — clamping `rate` to `[0, 0.99]` first so a misconfigured `EmergencyRate` of 1.0 or above can't divide by zero or invert the budget — which reduces to the historical `× 2` exactly at the detector's unchanged 0.50 default and scales further for any other calibration (e.g. `MaxMutations=2`, `EmergencyRate=0.75` now budgets 8 mutations, not 4). **Durable quality-diversity archives (ADR-033):** The island/QD evolution state is no longer rebuilt from scratch on every tool call. `IslandModel.Save`/`Load` (`internal/evolution/island.go`) persist the model (islands, generation, cumulative migrations) as JSON — atomic tmp+rename under the same ADR-024 `acquireExperienceLock` flock the ExperienceBank uses — and `Load` *merges* rather than clobbers: disk-only domains are adopted, memory-only domains survive, and an overlapping domain unions its individuals deduped by genome with the fitter copy winning (`mergeIslandPopulation`); **Cross-domain experience transfer closes the island model's own feedback loop (2026-07-13, ADR-062):** `IslandModel.Migrate`'s per-domain-pair step already copies elite individuals from a fitter source island into a weaker target island; the experience that made those elites fit did not travel with them. `ExperienceBank.TransferExperiences(sourceTree, _)` had been a stub that ignored its `sourceTree` argument entirely and queried `targetTree` through the Jaccard-similarity `Retrieve` path instead — the returned entries carried no actual link to the domain the individuals migrated *from*. It now calls `RetrieveByTreeType(sourceTree, 5)`, so the entries returned are genuinely `sourceTree`'s own top-quality experiences. A new `ExperienceBank.SeedDomain(sourceTree, targetTree)` copies up to 5 of those entries into `targetTree`'s own pool — each copy gets a fresh ID (so it never collides with or dedupes against the original), is re-tagged with `TreeType = targetTree`, and has `TimesReused`/`CreatedAt` reset — so a later `RetrieveByTreeType(targetTree, ...)` (the same call `EvolveWithExperience`'s warm-start and the gardener's `biasCandidatesWithExperience` already make, §8.5 ADR-017/ADR-021) surfaces them as native contributions to the target domain's own mutation biasing. `IslandModel` gains an optional `Bank *ExperienceBank` field (JSON-excluded, caller-wired); when set, `Migrate` calls `Bank.SeedDomain(srcDomain, tgtDomain)` for every domain pair that actually migrated at least one individual this cycle. A nil `Bank` leaves migration exactly as experience-agnostic as before. This is milestone 4/4 of the "Close the experience-grounded evolution feedback loop" (Q2 Evolvability) program: mutation experience now compounds not only across restarts (ADR-017/ADR-018) and across the daemon/gardener binaries (ADR-021/ADR-022), but across sibling domain trees inside a single island model. Covered by tests in `internal/evolution/island_model_test.go`. ⚠️ `bt_evolve_island` (`cmd/bt-agent/tools.go`) still constructs its `IslandModel` via the bare `NewIslandModel(interval, rate)` constructor and never sets `.Bank`, so the transfer is reachable and tested but not yet wired into the one production caller of `IslandModel.Migrate` — a follow-up wiring step, not a code gap.

**Structural safety gate on the gardener's live acceptance loop (2026-07-14, ADR-088):** `evolution.MetaValidator` (`internal/evolution/meta_validator.go`) had existed only as a tested, callerless P0 safety layer — its structural/expert-antipattern/regression checks combine into a `MetaAccept`/`MetaWarn`/`MetaReject` decision, but nothing in the gardener's live cycle ever consulted it. `Gardener.evolveTreeV2` (`internal/gardener/evolve_v2.go`) now calls `MetaValidator.ValidateMutation(tree, candidateTree, currentFitness.Composite, candidateFitness.Composite)` — passing the pre-mutation tree as baseline and the mutated clone as candidate — as the last check before a candidate is committed, *after* the `QuickValidate` benchmark score, the pre-score regression check, and `QualityGate.ValidateFor` have all already accepted it: a `MetaReject` decision still rejects the candidate, catching the structural failure classes (empty selectors, unbounded retries, expert antipatterns, oversized/over-deep candidates, >2.5x-baseline node-count growth) those fitness/quality/SLO gates never inspect. The check is wired through a new optional `Config.MetaValidator *evolution.MetaValidator` field — nil (the historical default for any caller that doesn't set it) preserves fitness-only acceptance exactly as before — and `cmd/bt-gardener/config.go`'s `buildGardenerConfig` sets it to `evolution.NewMetaValidator(evolution.MetaValidatorConfig{})` (production-default thresholds: `MinScore` 0.70, `MaxRegression` 0.20, `MaxNodes` 120, `MaxDepth` 8) for the daemon's real evolution cycles. Pinned by `TestEvolveTreeV2_MetaValidatorRejectsStructurallyBrokenMutation` (`internal/gardener/evolve_v2_test.go`), which shows the same fixture candidate accepted with `MetaValidator: nil` and rejected once a strict (`MinScore: 1.0`) validator is wired in.

**Durable pre-mutation snapshots and operator-triggered rollback (2026-07-15, ADR-093):** `gardener.Config.SnapshotDir` (`internal/gardener/gardener.go`) was already populated in production (`cmd/bt-gardener/config.go`) but had zero readers — the pre-mutation tree state existed only as the in-memory `originalTree` clone `evolveTreeV2` uses for that same cycle's own ACCEPT/ROLLBACK comparison ([§6.2](06-runtime-view.md)), so a process crash mid-cycle lost it entirely, and a bad mutation already committed by a *prior* cycle had no recovery path short of hand-editing the tree file. `evolveTreeV2` now calls the existing `evolution.SnapshotTree(tree, entry.Name, g.cfg.SnapshotDir)` (`internal/evolution/quality_gate.go`) right before the mutation loop begins, persisting the pre-cycle tree to `snapshot_<name>.json` under the snapshot directory (a non-fatal warning on failure). A new `Registry.RollbackTree(name, snapshotDir)` (`internal/gardener/gardener.go`) calls the paired `evolution.RestoreTree` and durably re-persists the restored tree via the existing `SaveTree`, returning an error for an unregistered tree name rather than silently no-op'ing. A new `GardenerRollbackTool`, mirroring `GardenerStatusTool`/`GardenerRunCycleTool`, registers this as the `gardener_rollback` langchain tool (`cmd/bt-gardener/main.go`) so an operator or LLM agent can trigger recovery directly. Pinned by `TestEvolveTreeV2_SnapshotsTreeBeforeMutation`, `TestRegistry_RollbackTree`, `TestRegistry_RollbackTree_UnknownTree`, and `TestGardenerRollbackTool_CallRestoresSnapshot`.

**Multi-revision snapshot history and automatic fail-closed rollback (2026-07-15, ADR-115):** ADR-093's snapshot/rollback pair above only ever kept one slot per tree — `SnapshotTree` overwrote `snapshot_<name>.json` every cycle, so a regression only discovered several cycles after it was introduced had nothing to roll back to but the *already-regressed* immediately-preceding state, and `RollbackTree` was reachable only by an operator or LLM agent invoking `gardener_rollback` — a disabled `QualityGate` merely paused mutations and left the tree frozen in its regressed state until process restart. **Milestone 1** replaces the single overwritten file with an accumulating history: `SnapshotTree` (`internal/evolution/quality_gate.go`) now writes each call to a sequentially-numbered `snapshot_<treeName>_<seq>.json` and appends the new sequence number to a `snapshot_<treeName>.index.json` index, never overwriting an earlier revision; a new `ListRevisions(treeName, snapshotDir)` reads that index back, and `RestoreTreeRevision(treeName, snapshotDir, revision)` loads any specific one — `RestoreTree` is now a thin wrapper that resolves to the newest entry in `ListRevisions`, preserving its existing callers' behavior exactly. **Milestone 2** wires automatic rollback into the fail-closed path: the `QualityGate.IsDisabledFor` check in `evolveTreeV2` (`internal/gardener/evolve_v2.go`) moved earlier, ahead of the pre-mutation `SnapshotTree` call (snapshotting the regressed state first would make it the new "most recent" revision and defeat the rollback), and now calls `g.cfg.Registry.RollbackTree(entry.Name, g.cfg.SnapshotDir)` to restore the tree's last-known-good revision the same cycle the gate trips, instead of only skipping that cycle's candidates. **Milestone 3** makes the activity observable: `CycleMetrics.Rollbacks` — already populated by the fail-closed path above but silently dropped by `MetricsTracker.Save()` — is now summed into `metricsDocument.TotalRollbacks` (`internal/gardener/gardener.go`) alongside the existing `TotalCrisisInterventions`/`TotalImprovements` aggregates, and `dashboard.loadGardenerMetrics()` (`internal/dashboard/metrics.go`) reads it into a new `GardenerMetrics.Rollbacks` field so a recorded rollback cycle is visible on the dashboard's gardener panel without replaying `history`. ⚠️ The gap ADR-093's own Consequences flagged still holds for the automatic path too: rollback restores unconditionally, without re-running `QualityGate.ValidateFor`/`MetaValidator.ValidateMutation` against the restored tree and without resetting the tree's fail-streak (`ResetFailCount`) — a tree that auto-rolls-back stays gate-disabled (mutations paused) until a process restart clears `failCounts`; it is simply no longer left sitting in the regressed state while paused. Pinned by `TestSnapshotTreeMultiRevision`, `TestListRevisionsEmpty` (`internal/evolution/quality_gate_test.go`), `TestEvolveTreeV2_DisabledGateTriggersAutomaticRollback` (`internal/gardener/evolve_v2_test.go`), `TestMetricsTracker_SaveAggregatesRollbacks` (`internal/gardener/gardener_test.go`), and `TestLoadGardenerMetricsParsesRollbacks` (`internal/dashboard/metrics_test.go`).

**Evolution kill switch (2026-07-15, ADR-098):** `Registry.DeactivateAll()` (`internal/gardener/gardener.go`) — sets `Active=false` on every registry entry and returns the previous active count, and is already what `evolveTreeV2`'s per-tree loop consults (`if !entry.Active { continue }`) to skip a tree — shipped fully tested but with no caller besides its own test, so halting every tree's evolution meant killing the `bt-gardener` process outright. A new `GardenerDeactivateAllTool`, mirroring the existing `GardenerStatusTool`/`GardenerRunCycleTool`/`GardenerRollbackTool` langchain-tool pattern, registers it as `gardener_deactivate_all` (`cmd/bt-gardener/main.go`) and reports `{"deactivated": <count>}` — the number of trees that were active before the call — so an operator or the langchain gardener agent can halt all evolution without a restart. Because `Active` is never persisted to disk (`Registry.loadAll`/`addBuiltin` always set it `true`), a subsequent daemon restart re-activates every tree — the kill switch is a live-process control, not a durable one. Pinned by `TestGardenerDeactivateAllTool_CallDeactivatesAllTrees` (`cmd/bt-gardener/main_test.go`).

**Gardener-embedded transposition table and deterministic eviction (2026-07-15, ADR-094):** Program "Q2 Evolvability — Wire the Stockfish transposition-table search into the gardener's live evolution loop," milestones 1–3/3. Before this, `evaluator.TranspositionTable` (`internal/evaluator/stockfish.go`) was reachable only through the standalone `bt-evaluator` MCP binary — the gardener's own 24/7 cycle never touched it, so cached `(tree, task)` evaluations reset every time `bt-evaluator` restarted and the gardener re-evaluated positions it had already scored. **Milestone 1:** a new `Config.TranspositionTablePath` (`internal/gardener/gardener.go`), when set, backs a lazily-constructed `*evaluator.TranspositionTable` cached on the `Gardener` (`transpositionTable()`, `internal/gardener/evolve_v2.go`, bounded at `transpositionTableMaxSize` = 5000 entries) — `evolveTreeV2` calls `tt.Store` immediately after computing `baseFitness`, before the evidence gate can short-circuit the rest of the pipeline, so every processed tree contributes an entry regardless of downstream gating; `RunCycleV2` calls `tt.Save()` right after `MetricsTracker.Save()`, on the same per-tree persistence cadence (a save failure logs a non-fatal warning), so the cache survives a gardener restart instead of living only in the separate `bt-evaluator` process. **Milestone 2:** `CycleMetrics` gains `DeepSearchUsed`/`DeepSearchDepth`/`TTHitRate` (`internal/gardener/gardener.go`); once the mutation loop finishes, `evolveTreeV2` runs `evaluator.IterativeDeepening(tree, records, tt, deepSearchMaxDepth)` (capped at depth 2) whenever a table is configured, populating those fields from the returned `DeepeningResult` — metrics-only this milestone, the deep-search result does not yet feed back into mutation selection (resolved 2026-07-15 by ADR-107, below). Both fields stay zero-valued when no table is configured. **Milestone 3:** `TranspositionTable.Store`'s over-capacity eviction and `load`'s startup trim-to-`maxSize` path both previously deleted an arbitrary entry via Go's randomized map iteration order. `TranspositionEntry` gains an `InsertedAt int64` marker, stamped from a monotonic `TranspositionTable.nextSeq` counter on every `Store` call (insert or overwrite); a new `evictLowestValueEntry` helper deterministically removes the entry with the lowest `InsertedAt` — the one least recently written, not necessarily the fittest — and both eviction sites now call it instead of duplicating ad hoc map-trim logic. `load()` fast-forwards `nextSeq` past the highest `InsertedAt` found on disk so freshly loaded entries can't collide with newly assigned sequence numbers. ~~⚠️ `cmd/bt-gardener/config.go`'s `buildGardenerConfig` does not set `TranspositionTablePath`, so the daemon's real evolution cycles do not yet populate or persist a table or run deep search — this lands the same way `Config.SelectorStatsPath` did before ADR-079 wired it in: implemented, tested, and off by default in production until a follow-up sets the path.~~ — resolved 2026-07-15 (ADR-114 milestone 2): `buildGardenerConfig` now sets `TranspositionTablePath` to `<metricsDir>/transposition`, so deep search runs live in every scheduled `bt-gardener` cycle and `gardener_run_cycle` call. Since the same landing (ADR-114 milestone 1), the deep-search-applied mutation (ADR-107) is also cloned and re-validated through `MetaValidator.ValidateMutation` before it is applied to the live tree, mirroring the greedy loop's own gate and the ADR-112 `ValidationGate` re-check that already covered this path — reverting to the pre-deep-search tree on `MetaReject` the same way. ADR-114 milestone 3 aggregates `CycleMetrics.DeepSearchUsed`/`TTHitRate` into `gardener-metrics.json`'s `metricsDocument` as `total_deep_search_cycles`/`avg_tt_hit_rate` (`MetricsTracker.Save`, `internal/gardener/gardener.go`), alongside the existing `total_crisis_interventions` aggregate (ADR-032) — no dashboard consumer reads these two fields yet. Pinned by `TestRunCycleV2_TranspositionTablePersistsAcrossGardenerInstances` (`internal/gardener/evolve_v2_test.go`, milestone 1); `TestEvolveTreeV2_DeepSearchMetrics_PopulatedWhenTTConfigured`/`TestEvolveTreeV2_DeepSearchMetrics_ZeroWithoutTranspositionTable` (`internal/gardener/gardener_test.go`, milestone 2); and `TestTranspositionTable_Store_EvictsLowestValueDeterministically`/`TestTranspositionTable_Store_EvictsLowestValueRepeated`/`TestTranspositionTable_Store_EvictionPreservesLowestAmongSurvivors`/`TestTranspositionTable_StoreProbeRoundTrip`/`TestTranspositionTable_SaveLoadRoundTrip` (`internal/evaluator/stockfish_test.go`, milestone 3).

**Adaptive, track-record-driven generation budgets (2026-07-15, ADR-119):** All five benchmark-gated tools (ADR-096/ADR-111/ADR-113 above) previously fell back to the same hardcoded `params.Generations = 10` whenever a caller omitted the parameter, regardless of how often that tree's evolved winners had been getting rejected by `benchmarkGateEvolvedWinner`. `evolution.TrackRecord` (`internal/evolution/track_record.go`) closes that gap: a `Runs []TrackRecordRun` archive of accept/reject outcomes, capped at 500 entries (mirroring `ExperienceBank`/`QTable`) and persisted via the same atomic tmp+rename-under-`acquireExperienceLock` idiom every other durable archive in this package uses. `RecommendedGenerations(defaultGenerations)` looks at the most recent `trackRecordWindow` (5) runs and, when at least one was rejected, scales the default up by `1 + rejection_rate` (`math.Round`) — an all-accepted or cold-start history returns the default unchanged. `WinRate()` reports the acceptance fraction over the same window (1.0 when cold). Each of `bt_evolve_qd`, `bt_evolve_multiobjective`, `bt_evolve_pareto`, `bt_evolve_qlearning`, and `bt_evolve_island` (`cmd/bt-agent/tools.go`) now loads one shared `trackRecordArchivePath(treeID)` (`~/.go-bt-evolve/track_record-<tree>.json`, sanitized the same way as the other per-tree archives — ADR-034) before computing its `Generations` fallback, calls `track.Record(gateRejected)` with that call's own `benchmarkGateEvolvedWinner` verdict regardless of which of the five tools produced it, and re-saves — so a regression any one algorithm discovers on a tree raises every other algorithm's next generation budget on that same tree, not just its own. The result JSON gains `track_record_win_rate` and `track_record_recommended_generations` alongside the existing `benchmark_gate_rejected` field (and a non-fatal `track_record_load_error`/`track_record_save_error` on I/O failure) so the adaptive driver is observable rather than purely internal state. Pinned by `TestBTEvolveQDAndMultiObjectiveShareTrackRecordDrivenGenerationBudget`, `TestBTEvolveParetoAndQLearningShareTrackRecordDrivenGenerationBudget`, and `TestBTEvolveIslandSharesTrackRecordDrivenGenerationBudget` (`cmd/bt-agent/tools_test.go`) — `internal/evolution/track_record.go` itself has no dedicated unit test file; its `Record`/`RecommendedGenerations`/`WinRate`/`Save`/`Load` behavior is exercised only indirectly through those three `cmd/bt-agent` integration tests.

## 8.6 Error Resiliency

**What:** SafeGo (panic recovery) + CircuitBreaker (3-state) + RetryWithBackoff (full jitter, 3 classes) + DeadLetterQueue (persistent JSON). (→ ADR-007)

**Why:** LLM calls can fail (Ollama OOM, DeepSeek rate limits, network timeouts). Goroutines must not crash the process. Failed work must not be silently lost.

**Where:** `internal/reliability/` — SafeGo, CircuitBreaker, RetryPolicy, DeadLetterQueue. Applied in scheduler runner (`main.go:276`), ChainAction execution, and — since 2026-07-12 (ADR-046) — the fan-out goroutines in `internal/a2a/auction.go` (`CollectBids`), `internal/dashboard/workflow_orchestrator.go` (`executeParallel`), and `internal/knowledge/embeddings.go` (`BuildIndex`). Also since 2026-07-12 (ADR-047): the 18 per-command fan-out goroutines in `internal/engine/reactive_parallel.go` (`BuildReactiveParallel` and its standalone twin `runReactiveParallel`). Also since 2026-07-12 (ADR-048, milestones 1–3/5): `internal/llm/health.go`'s `HealthMonitor.Start()` (initial probe and ticker-loop goroutines), `internal/security/security.go`'s `RequestTimeoutMiddleware` (the per-request handler goroutine), and `internal/reliability/scalability_probe.go`'s `ProbeMultiNodeDashboard` (per-node probe fan-out). Also since 2026-07-12 (ADR-049, milestones 4–5/5, closing the program): `cmd/bt-dashboard/pipeline_handlers.go`'s `handlePipelineRun` goroutine, and `cmd/bt-agent/main.go`'s `kg.BuildIndex()` startup goroutine and DLQ replay-scan ticker loop. Also since 2026-07-13 (ADR-053): `internal/llm/acp.go`'s ACP-subprocess-stdout scanner goroutine (`startScanJSONLines`), the synchronous `reliability.Recover` guarding each model's call in `internal/llm/fallback.go`'s `FallbackLLM.generate` loop, and the two remaining bare `go` spawns in `cmd/bt-agent/main.go` — the scheduler-start callback registration and the A2A server-start loop. Also since 2026-07-13 (ADR-054, closing the same program's milestone 4/4): a dedicated `reliability.CircuitBreaker` field on `ACPClient` itself (`internal/llm/acp.go`), guarding subprocess start/session-setup, not just the goroutines around it. Also since 2026-07-13 (ADR-059, milestones 1–3/5): `internal/agent/webhook_publisher.go`'s `WebhookPublisher.Attach` background loop, `internal/security/security.go`'s `RateLimiter.cleanup` (`NewRateLimiter`), and `internal/security/session.go`'s `SessionStore.cleanupLoop` (`NewSessionStore`) — three more production-wired goroutines the ADR-046→049/053 passes missed. Also since 2026-07-13 (ADR-060, milestones 4–5/5, closing the program): `internal/security/apikey.go`'s `KeyRotationScheduler.loop` (plus a synchronous `reliability.Recover` around each `onRotate` callback invocation), `internal/config/watcher.go`'s `ConfigWatcher.loop`, and `internal/reliability/heartbeat.go`'s `NodeHeartbeat.cleanupLoop` (both constructors) — all three previously dormant with no `cmd/*/main.go` caller.

**Effect:** The platform degrades gracefully. A single LLM failure doesn't cascade. Failed tasks are preserved for inspection.

**SafeGo adoption across A2A/dashboard/knowledge fan-out (2026-07-12, ADR-046):** three production `go func()` spawns previously ran without panic recovery, each reachable from untrusted or pluggable per-item logic — `CollectBids` fans one goroutine out per candidate bidder over unmarshaled responses from remote agents, `executeParallel` fans one out per parallel workflow sub-step, and `BuildIndex` fans one out per tree, synchronously drained by a `for`-range receive loop sized to `len(kg.Trees)`. All three now wrap their goroutine body in `reliability.SafeGo`. `CollectBids` uses the default handler (a panicking candidate is simply absent from the returned bids, matching its existing best-effort semantics). `executeParallel` supplies a handler that writes `StepResult{Outcome: "error", Error: "panic: …"}` at the panicking sub-step's index so siblings still complete and the parent step's aggregate outcome degrades to `"partial"` instead of the process crashing. `BuildIndex` supplies a handler that sends a `result{err: …}` on the per-tree channel — without it, a panic before the channel send would leave the fixed-count receive loop blocked forever, a deadlock rather than just a crash. Pinned by `TestCollectBids_SurvivesPanickingCandidate` (`internal/a2a/auction_test.go`), `TestWorkflow_ParallelSubStepPanicRecovered` (`internal/dashboard/workflow_orchestrator_test.go`), and `TestBuildIndex_PanicRecovered` (`internal/knowledge/embeddings_test.go`). `internal/engine/reactive_parallel.go`'s 18 `go func()` fan-out sites remained unwrapped at the time — the largest residual gap, out of scope for this program — until ADR-047 closed it on the same day.

**LLM subprocess and fallback-chain hardening (2026-07-13, ADR-053):** the ADR-046→049 sweep never reached the LLM call path itself. `ACPClient.GenerateCtx`'s stdout scanner (`scanJSONLines`, `internal/llm/acp.go`) parses arbitrary JSON-RPC lines from an external ACP subprocess and ran as a bare `go` statement; it now launches through a `startScanJSONLines` helper wrapping it in `reliability.SafeGo`, with a `PanicHandler` that reports the panic on the same `scanErr` channel the scanner's own I/O errors use, so a malformed-output panic degrades the one in-flight `GenerateCtx` call instead of crashing the daemon. `FallbackLLM.generate` (`internal/llm/fallback.go`) drives its per-model `call(model.LLM)` invocation through a synchronous `reliability.Recover` keyed by the model's name; a panic is now converted into a wrapped error appended to `errs` and the loop proceeds to the next fallback model, matching the function's existing error-tolerant contract instead of one bad model panicking the whole fallback chain. Separately, `cmd/bt-agent/main.go` still had two bare `go` spawns the ADR-046→049 program's four passes missed — `globalSched.Start(...)`'s callback registration and the `a2aSrv.Start()` loop — both now wrapped in `reliability.SafeGo` (`"scheduler-start"`, `"a2a-server-start"`), matching the `kg-build-index`/`dlq-replay-scan-ticker` pattern ADR-049 established in the same file. Pinned by `TestStartScanJSONLines_ReaderPanicRecoveredOnScanErr` (`internal/llm/acp_test.go`), `TestFallbackLLM_GenerateRecoversPanicAndTriesNextModel` and `TestFallbackLLM_GenerateAllPanicReturnsAggregatedError` (`internal/llm/fallback_test.go`), and `TestDaemonWrapsSchedulerAndA2AStartWithSafeGo` (`cmd/bt-agent/main_test.go`).

**ACP subprocess failure-storm circuit breaker (2026-07-13, ADR-054, closes the program's milestone 4/4):** ADR-053 stopped a panicking scanner or fallback model from crashing the process, but a *cleanly failing* ACP subprocess — a missing binary, a crash-looping agent — still respawned on every single `GenerateCtx` call, with no memory of the prior failures. `ACPClient` now carries its own `breaker *reliability.CircuitBreaker`, constructed in `NewACPClient` as `reliability.NewCircuitBreaker("acp-subprocess:"+cfg.Command, 3, 60*time.Second)`. `GenerateCtx` calls `breaker.Allow()` before doing any subprocess work and, if the circuit is open, returns immediately with an error naming the open circuit instead of spawning another doomed process; every failure exit on the subprocess-start/session-setup path (`StdinPipe`/`StdoutPipe`/`cmd.Start`/`initialize`/`session/new`/missing `sessionId`/the prompt `request` call) calls `breaker.RecordFailure()`, and the one success path calls `breaker.RecordSuccess()`. Because `NewProvider` (`internal/llm/provider.go`) constructs one long-lived `ACPClient` per daemon process, the breaker's state persists across calls for the process lifetime, so three consecutive subprocess failures open the circuit for 60s before a half-open probe is allowed through. Pinned by `TestACPClientCircuitBreakerShortCircuitsRepeatedSubprocessFailures` (`internal/llm/acp_test.go`), which points `ACPClient` at a helper subprocess mode that always exits immediately and asserts both that the process launch count stays below the call count once the breaker trips and that the final error names the open circuit.

**Second-wave SafeGo adoption in webhook and cleanup goroutines (2026-07-13, ADR-059, milestones 1–3/5):** three more production-wired `go` spawns the ADR-046→049 and ADR-053 sweeps missed. `WebhookPublisher.Attach` (`internal/agent/webhook_publisher.go`, wired at `cmd/bt-agent/main.go:593`) forwards every `AgentBus` event's arbitrary `Data interface{}` through `json.Marshal` and an HMAC-signed POST to Hermes; its `go p.loop()` now runs via `reliability.SafeGo("webhook-publisher-loop", ...)`, and — because a panic that kills the loop itself would silently stop forwarding all future events even after being recovered — `loop()` additionally wraps each `p.handleEvent(event)` call in a synchronous `reliability.Recover("webhook-publisher-handle-event", ...)`, so one malformed payload degrades only that event. `NewRateLimiter`'s `go rl.cleanup()` (`internal/security/security.go`, wired at `cmd/bt-dashboard/main.go:251`, distinct from `RequestTimeoutMiddleware`'s already-guarded panic path, ADR-048) and `NewSessionStore`'s `go ss.cleanupLoop()` (`internal/security/session.go`, wired at `cmd/bt-dashboard/main.go:214` and `:337`) are now launched via `reliability.SafeGo` too. Unlike the webhook loop, neither cleanup goroutine got the two-layer loop-plus-per-tick-`Recover` treatment ADR-048 and ADR-049 established for `internal/llm/health.go`'s ticker and the DLQ replay-scan ticker: `SafeGo` wraps the whole ticker loop, so a panicking cleanup tick (e.g. a corrupted bucket/session entry) is recovered once and the process survives, but that goroutine then exits and periodic bucket/session cleanup silently stops for the rest of the process's life. Pinned by `TestWebhookPublisherLoop_PanicRecovered` (`internal/agent/webhook_publisher_test.go`), `TestRateLimiterCleanup_PanicRecovered` (`internal/security/security_test.go`), and `TestSessionCleanup_PanicRecovered` (`internal/security/session_test.go`) — all subprocess-based, mirroring `TestHealthMonitorStart_PanicRecovered`, since an unrecovered panic must be observed from outside the panicking process. Three bare `go` spawns remain out of this pass's scope, all currently dormant with no production caller: `internal/security/apikey.go`'s `KeyRotationScheduler.loop`, `internal/config/watcher.go`'s `ConfigWatcher.loop`, and `internal/reliability/heartbeat.go`'s `NodeHeartbeat.cleanupLoop` (both constructors).

**What:** Output validation before declaring success. Minimum length, error pattern detection, structure scoring (markdown, bullets, code blocks). QualityScore 0.0-1.0.

**Why:** LLMs sometimes produce truncated/garbage output (e.g., max_tokens=10 producing a few words). Without validation, agents report "success" with useless output.

**Where:** `internal/engine/tree.go:validateOutputQuality()`. Applied after every RunTask() and in ReflectOnOutcome action; since 2026-07-13 (ADR-084) also gates `registry.go`'s `MarkSuccessful` action directly, so the `OutcomeSelector`'s own success/retry/escalate routing (§8.1) depends on the same check rather than only post-hoc scoring. Since 2026-07-14 (ADR-085), `RunTask`'s own terminal call to `validateOutputQuality` also acts on the result directly — flipping `bb.Outcome` to Failure for low-quality, non-structured, non-`Sandbox` output — covering trees that terminate without ever reaching the `OutcomeSelector` at all.

**Effect:** Structured zero-LLM output (alert_router, agent_monitor) scores correctly. Garbage output is flagged. Quality scores feed into fitness evaluation. Garbage/short output at the `OutcomeSelector` now triggers `SelfCorrect` and, if that also fails, a real `EscalateToDeepSeek` LLM call, instead of being marked successful outright. ## 8.12 A2A Auction Task Allocation

**What:** A contract-net allocation protocol over the A2A transport. `Auctioneer.RunAuction` composes announce → evaluate → dispatch end to end: it fans a `TaskAnnouncement` out to candidate agents via `CollectBids`, each candidate scores the announcement against its own agent card with `ScoreAnnouncement` and answers with a `Bid` (cost/confidence) or declines — `CollectBids` attributes each collected bid to the identity the announcement was delivered under (the candidates-map key), not the untrusted self-reported `BidderName`, so a candidate that misreports its name still resolves against the candidates map at Award/dispatch time — a `ScoreEvaluator` awards the lowest-cost eligible bid, and the winner alone is dispatched the real task text — returning an `AuctionResult` (Award + execution result); `CollectBids` bounds each candidate's fan-out by a per-candidate deadline derived from the announcement's `Deadline` (a 30s `defaultBidDeadline` when unset) so one hung candidate cannot stall the auction — and the winning-agent dispatch reuses that same `candidateContext` deadline rather than the raw caller context, so a winner that hangs after Award cannot block `RunAuction` indefinitely — and `RunAuction` rejects an announcement with an empty `Description` before dispatch. Since 2026-07-13 (ADR-064), winner dispatch is both honest and resilient: `BTAgentClient.SendTask`'s new `interpretSendResult` helper returns a non-nil error for every non-success outcome (an incomplete/failed/canceled/rejected `Task` state, a `Message` with no text parts, or an unrecognized response type) instead of formatting the failure as a successful-looking string — `RunAuction` retries a failing dispatch up to `winnerDispatchRetries` (3, full-jitter-free backoff 50ms–500ms) before giving up, and a per-winner `reliability.CircuitBreaker` (keyed `"a2a.auction.winner."+name`, threshold 3, cooldown 30s) trips after repeated failures so a persistently-failing winner is refused outright on later auctions instead of being re-dispatched to and re-timed-out on every single one. Since 2026-07-13 (ADR-065), that breaker survives beyond a single `RunAuction` call: `NewPersistentAuctioneer` (the constructor `AuctionDelegate` now uses in production, in place of the ad hoc-scoped `NewAuctioneer`) routes `winnerBreaker` lookups through a process-wide `winnerBreakerStore` instead of the `Auctioneer`'s own `breakers` map, so a failure count accumulates across every engine tick — not just repeated calls on one `Auctioneer` instance, which production never reused anyway — and the store round-trips through `agent.CircuitBreakersFile()` after every dispatch outcome, so a tripped breaker also survives a process restart. `NewAuctioneer` keeps the original per-instance, disk-free `breakers` map for ad hoc/test callers. On the responder side, `BTAgentExecutor.Execute` detects an incoming JSON announcement and replies with a bid artifact on a completed task instead of running the announcement JSON as literal task text, declining silently when ineligible. Since 2026-07-15 (ADR-108), that branch delegates to the already-tested `RespondToAnnouncement` (parse → score → marshal) instead of duplicating its logic inline, and scores the announcement against a card held in a new `BTAgentExecutor.CardCache` — populated from the same `cards` map `NewServer` builds for `Server.CardCache` — rather than re-deriving (and re-`SignAgentCard`-ing) a fresh card from the tree definition on every inbound request; a fresh `ConvertToAgentCard` conversion is used only as a fallback when no cached card exists for the agent. An engine-side `AuctionDelegate` behavior-tree action makes this auction reachable from within any tree: it reads `bb.Task` and delegates to an injected `AuctionDelegateFn(task, chainState) → (result, awarded, err)` hook — the same injection-hook pattern as `DelegateToA2AFn`/`DelegateToTreeFn`, used because `internal/a2a` imports `internal/engine` and the dependency cannot be reversed — falling back, when no eligible bidder is awarded, to running the task through a delegate tree named by `chain_state.delegate_tree_id` via `DelegateToTreeFn`.

**Why:** The three stages (announce/collect, evaluate→Award, dispatch) existed but nothing wired announce→evaluate→dispatch together, so a picked Award was never acted on; and a real bt-agent server treated the announcement JSON as literal task text, so no production agent could ever return a well-formed Bid and the fan-out was inert. Scoring bids from an agent's own card — confidence as the fraction of card capabilities the task demands, cost as the count of irrelevant ones — lets a focused specialist win over a diluted generalist.

**Where:** `internal/a2a/auction.go` (Auctioneer, RunAuction, AuctionResult, ScoreAnnouncement, ScoreEvaluator, the winner `reliability.CircuitBreaker`/`RetryPolicy` pair, `NewPersistentAuctioneer`, the process-wide `winnerBreakerStore`/`winnerBreakers`, and the production `AuctionDelegate` / `AuctionCardsFn` / `candidateContext` seams), `internal/a2a/client.go` (`BTAgentClient.SendTask`, `interpretSendResult`), `internal/a2a/server.go` (RespondToAnnouncement, parseAnnouncement, the bid-aware Execute branch, `BTAgentExecutor.CardCache`, `Server.AuctionCardSource`, `Server.RefreshCards`), `internal/a2a/card.go` (EligibleBidders, treeTags), `internal/a2a/signing.go` (`SignAgentCard`/`VerifyAgentCard`, and — since 2026-07-14 — `cardSignatureValid`), `internal/engine/actions_a2a.go` (the `AuctionDelegate` action and `AuctionDelegateFn` injection seam), `internal/agentexec/wiring.go` (installs `engine.AuctionDelegateFn = a2a.AuctionDelegate` at link time), `cmd/bt-agent/main.go` (installs `a2a.AuctionCardsFn` from the live card registry at startup), `internal/domains/trees.go` (the `auction_demo` tree). Since 2026-07-13 (ADR-073), also `internal/dashboard/executor.go` (`PickTreeForTask`'s `isAuctionShapedTask`/`auctionKeywordPattern`) and `internal/engine/actions_a2a.go` (the exported `AuctionTaskKeywords` it mirrors).

**Effect:** Multi-agent task allocation now closes end to end: an auctioneer can announce, collect real bids from live per-agent endpoints, award the best-fit agent, and dispatch it the work. Unreachable, silent, malformed, foreign-task, and name-misreporting candidates are tolerated without failing the auction. Since ADR-064, a winner that itself fails is no longer indistinguishable from one that succeeded (dispatch failures are real `error`s, not success text describing the failure) and is no longer dispatched to unconditionally forever (bounded retry, then a per-winner circuit breaker) — and since ADR-065, that circuit breaker's failure count is no longer reset to zero on every single engine tick, because `AuctionDelegate` now dispatches through `NewPersistentAuctioneer(newAuctionCollector())` instead of a fresh, breaker-state-discarding `NewAuctioneer(...)`. The engine `AuctionDelegate` node and its `AuctionDelegateFn` seam are now injected in production: `internal/agentexec`'s `init` installs `engine.AuctionDelegateFn = a2a.AuctionDelegate` as a link-time side effect (so the node never reports *auction delegate not configured* once the binary is linked, guarded by the binary-level `TestDaemonConfiguresAuctionDelegateHook`), and the daemon supplies the live candidate source at startup via `a2a.AuctionCardsFn = a2aSrv.AuctionCardSource()`. `AuctionDelegate` builds the candidate map (agent name → A2A URL) from the registered agents' A2A cards (`EligibleBidders` restricted by `RequiredTags`, resolved to `cardURL`), runs the `Auctioneer` over the real `BTAgentClient` transport, and honors `chainState` overrides — `auction_candidates` (a name→URL map that replaces the derived set), `auction_required_tags`, `auction_min_confidence`, and `auction_task_id` — for candidate selection and announcement shaping. A curated `auction_demo` domain tree (program milestone 5/5, `internal/domains/trees.go`) exposes the auction via `switch_tree` behind an `IsAuctionTask` gate. Earlier revisions fronted `AuctionDelegate` with separate `AnnounceTask` and `CollectBids` `Action` nodes so the tree "read as" the full protocol, but those names are unregistered in the engine and resolved to the permissive success fallback — a silent no-op that reported success while surfacing no announcement/bid evidence. Because `RunAuction` already performs the announce and collect stages inside `AuctionDelegate`, the honest tree collapses to that single real seam; the runtime test `TestAuctionDemoTreeHasNoSilentNoOps` fails if any node is a silent no-op. Since 2026-07-13 (ADR-073), `auction_demo` also gained a second production entry point: `internal/engine/actions_a2a.go`'s task-text keyword list (`auctionTaskKeywords`, feeding `IsAuctionTask`) was exported as `AuctionTaskKeywords` so `dashboard.PickTreeForTask` ([§6.3](06-runtime-view.md)) can mirror the same routing decision with a whole-word regex match (`isAuctionShapedTask`) and select `auction_demo` for auction/delegation-shaped task text — closing the gap where the dashboard's thinktank→task→sprint execution path ([§6.3](06-runtime-view.md)) could mint an auction-shaped task without ever routing it through the auction machinery.

**Card-integrity check on the trust boundary (2026-07-14, ADR-090):** `SignAgentCard`/`VerifyAgentCard` (a SHA-256 content hash, not a keyed/asymmetric signature) had existed since ADR-008 with no caller outside their own tests — a card could be edited after being cached with nothing to detect it. Both card-producing paths now attach one: `ConvertToAgentCard` (`internal/a2a/card.go`), the single origin point every registered-agent card passes through, appends a `SignAgentCard` result to `card.Signatures`; `handleGlobalAgentCard` (`internal/a2a/server.go`), which assembles the `/.well-known/agent-card.json` response ad hoc rather than via `ConvertToAgentCard`, signs it separately just before writing the response. On the consuming side, `auctionCandidates` (`internal/a2a/auction.go`) — the function that turns the live card registry into `AuctionDelegate`'s dispatchable candidate set, i.e. the actual trust boundary — now filters the registry through a new `cardSignatureValid` (`internal/a2a/signing.go`) before calling `EligibleBidders`: a card with no `Signatures` at all is trusted (signing is opt-in, so unsigned is the default and expected state for any card that predates this feature or was built outside `ConvertToAgentCard`), but a card whose trailing signature no longer verifies against the rest of its content — tampered after signing, or forged — is dropped from the candidate set before bidding rather than being auctioned to. Because the hash covers the whole card including prior signatures, `cardSignatureValid` re-verifies against the card with its own trailing signature stripped off. Pinned by `TestConvertToAgentCard_AttachesSignature`, `TestHandleGlobalAgentCard_ResponseIsSigned`, and `TestAuctionCandidates_RejectsTamperedCardSignature` (`internal/a2a/signing_test.go`). Because the hash is unkeyed, this defends against accidental corruption/staleness rather than a determined adversary who could simply recompute a valid hash over their own forged card — the property closed here is integrity-of-transit-and-cache, not authentication.

**Runtime card-registry refresh (2026-07-15, ADR-117):** `Server.CardCache` and `BTAgentExecutor.CardCache` (ADR-108, above) were each built once in `NewServer` from a single `BuildCardRegistry` snapshot and never revisited afterward — an agent created after the process started, via `bt_agent_create` or autopilot's `activateAutomation` (both of which call `Create` against the same live `*agent.Registry` the server was built from), was invisible to the per-agent endpoint, the global agent card, and `AuctionCardSource`'s candidate pool until a process restart re-ran `NewServer`. `Server.RefreshCards()` (`internal/a2a/server.go`) rebuilds the registry via `BuildCardRegistry` and reassigns both `s.CardCache` and, when non-nil, `s.Executor.CardCache` to the new map — a wholesale replacement of both sides together, resolving the caveat ADR-108 left open about `CardCache` never being reassigned. `cmd/bt-agent/main.go` wires it into a new `mcpDeps.refreshA2ACards` function field (nil whenever the A2A server failed to start, so callers must nil-check); both `bt_agent_create` (`cmd/bt-agent/tools.go`, covering both the direct-`Create` and `InstallFromTemplate` paths) and autopilot's `activateAutomation` (`cmd/bt-agent/autopilot.go`) call it immediately after their own `Create` call succeeds, logging a warning rather than failing the request if the refresh itself errors. A newly created or newly activated agent is therefore reachable over A2A/auctions the same tick it is registered, with no restart required. Pinned by `TestServer_RefreshCards_PicksUpAgentCreatedAfterStartup` (`internal/a2a/server_test.go`), which creates an agent after `NewServer` and asserts it appears in `Server.CardCache`, `Executor.CardCache`, and the `AuctionCardSource()` candidate pool only after `RefreshCards` runs.

## 8.13 Leaf-Node Structural Validation

**What:** A tree-authoring invariant enforced before build: node types whose `engine.buildNode` builders construct childless leaves — `Action`, `Condition`, `AlwaysSucceed`, and (since 2026-07-16, ADR-130) `ChainAction` — must not declare `Children`. Both validation entry points reject a violation: `walkValidate` (the 5-stage `ValidateTreeFull`) appends `node %q: leaf type %q must not declare children (got N)`, and the flat `validateNode` (`ValidateTree`, consumed by preflight / `BuildAndValidate` callers) appends `<name>: <type> leaf must not declare children`. The two paths share a single `leafNodeTypes` set so they cannot drift.

**Why:** `buildNode` silently discards `node.Children` for these types (e.g. `tree.go` `case "AlwaysSucceed"` returns a childless action ignoring any declared children). Before this rule an author could nest a subtree under such a leaf and lose it at build time with no validation signal — the same silent-no-op class the platform guards against elsewhere (§8.12, R11 in [§11](11-risks-debt.md)). Surfacing it as a validation error turns a silent structural mistake into an actionable message at both authoring choke points. `ChainAction` (`tree.go`'s `case "ChainAction":`, reading `ChainConfig` from node metadata via `BuildChainAction`) had the identical gap and joined the set for the same reason.

**Where:** `internal/engine/verifier.go` (`leafNodeTypes`, `walkValidate`), `internal/engine/validate.go` (`validateNode`), against the childless builders in `internal/engine/tree.go` (`buildNode`).

**Effect:** A leaf-type node carrying children fails validation instead of building into a runnable tree that quietly drops the subtree; the shared `leafNodeTypes` map keeps the deep (`ValidateTreeFull`) and flat (`ValidateTree`) validators in lockstep. Since 2026-07-16 (ADR-130), a `ChainAction` node declaring `Children` is rejected the same way, pinned by `TestVerifierFull_ChainActionRejectsChildren` (`internal/engine/verifier_test.go`).

## 8.14 Fleet-Wide Node Description Coverage

**What:** A tree-authoring invariant over the registered fleet: every node of every type — root, interior composites (Sequence, Selector, decorators), and leaves (Condition, Action, ChainAction) — in every registered domain tree — including, since 2026-07-05, the 13 generated `arc42:*` trees — must carry a non-empty `Description`, and every tree a non-empty `Descriptions` entry. The invariant extends beyond the `AllDomainTrees` registry to the production-reachable non-registry trees — the smoke-tested extras (`hermes_evolve` and the six `kanban_*` trees) and the resolver-reachable extras (`hermes_obsidian`, `superpowers_pipeline`) — guarded per node only, since `TestDescriptionsHaveNoOrphans` deliberately forbids them a root `Descriptions` entry. The `seq()`/`sel()` authoring helpers (`internal/domains/trees.go`) take a mandatory description parameter, so an undescribed composite cannot even be constructed through the helper API; the arc42 `chain()` helper (`internal/domains/arc42_trees.go`) likewise takes a mandatory description, so an undescribed LLM stage cannot be built either.

**Why:** Node descriptions are the human-readable rationale the gardener and the bt-agent `switch_tree` tool surface. Coverage grew incrementally — root `Descriptions` entries, then Conditions, then leaves — but interior composites stayed exempt: the helpers built every `StrategyRouter` Selector (the primary routing decision point) and every Sequence stage (`PreGate`, `BugDetection`, `BuildPath`, …) with a blank `Description`, so exactly the nodes that encode routing and stage semantics were the unexplained ones.

**Where:** `internal/domains/trees.go` (`seq`/`sel` signatures and their curated call sites), described composite literals across the other registered-tree files in `internal/domains/` and the evolution-built subtrees (`internal/evolution/goap_trees.go`, `internal/evolution/notebooklm_workflow.go`); guards in `internal/domains/domains_test.go` — `TestAllDomainTreeSelectorsHaveDescriptions` (router anchor) and the consolidated `TestAllDomainTreeNodesHaveDescriptions`, which walks every node of every curated registered tree, `TestNonRegistryDomainTreeNodesHaveDescriptions`, which applies the same full-node walk to the non-registry trees (`internal/domains/hermes_evolve.go`, `hermes_obsidian.go`, `kanban.go`), and `TestArc42DomainTreeNodesHaveDescriptions`, which applies it to the 13 `arc42:*` registry trees.

**Effect:** Every routing decision and execution stage in the registered fleet — curated and generated alike — is self-documenting at the node level, including the production-reachable trees outside the registry, whose composites and Action/ChainAction leaves were previously exempt; the consolidated full-node guards prevent any future tree from regressing on any node class, while the narrower sibling guards (root, condition, leaf, selector) remain as targeted regression anchors.

## 8.15 Validation-Gated Composition Activation

**What:** The `bt_blocks_compose` MCP tool treats operator input as a contract, not a hint. A non-empty `strategy` id that `resolveTree` cannot resolve is rejected with `unknown strategy tree %q` — via the shared `resolveStrategyTree` helper hoisted above all three compose branches (preset, task-tree, block-list) — instead of composing with the StrategyRouter silently omitted. With `save: true`, the composed tree reaches the tree store and replaces the live tree only after `engine.ValidateTree` returns no messages *and* `treeStore.Save` succeeds; either failure returns an MCP error carrying the validation messages or save error and leaves the active tree untouched. A gated save that actually happened is signalled explicitly by `"saved": true` in the success payload.

**Why:** Both prior behaviors were the §8.12/§8.13 silent-no-op class surfacing at the operator boundary: a strategy typo produced a tree that "read as" routed but had its requested condition-node routing amputated while still reporting `composed: true`, and an invalid composition — unknown node types, the same failure class the `auction_demo` tree hit at build time — was unconditionally activated as the live tree with its `Save` error discarded, so the operator learned nothing until the tree dead-lettered.

**Where:** `cmd/bt-agent/blocks_tools.go` (`resolveStrategyTree`, the gated `params.Save` block); pinned by `TestBTBlocksComposeRejectsUnknownStrategyTree` and `TestBTBlocksComposeSaveGatesActivation` (`cmd/bt-agent/blocks_tools_test.go`).

**Effect:** A composition either does exactly what was asked or fails loudly with an actionable message, and the live tree can no longer be replaced by a composition the engine's own validator would refuse. The same fail-loud sweep hardened the operator CLI: `requireNameArg` (`cmd/bt-agent-cli/main.go`, pinned by `TestRequireNameArg`) guards the `test`/`logs`/`delete` subcommands' positional agent-name read, printing `Error: agent name required` plus usage and exiting 1 where the unguarded `os.Args[2]` read previously panicked with index-out-of-range.

## 8.16 Self-Extending Claude Error Recovery

**What:** `ClaudeErrorHandler` — a self-extending recovery decorator wrapped around every domain-tree root. On subtree failure it first ticks previously generated recovery nodes guard-first (a matching guard condition selects the extension, so no LLM call is made when a known fix already applies); only when no extension resolves the failure does it make at most one read-only Claude Code call per error signature per cooldown (default 6h), asking Claude to propose a recovery node composed from the registered action/condition vocabulary. A validated proposal persists under `~/.go-bt-evolve/error_handler/` and is re-grafted as a child of the handler on every subsequent tree build (trees are rebuilt from the compiled catalog each scheduled run, so persistence — not in-memory state — is what makes a learned fix stick), then ticked immediately for the run that triggered it.

**Why:** The platform's other error-handling primitives (§8.6 SafeGo/CircuitBreaker/DLQ, [§6.5](06-runtime-view.md)) protect the process and preserve failed work, but neither one learns a fix for a specific, recurring subtree failure — every occurrence of the same error signature re-fails the same way until a human intervenes. `ClaudeErrorHandler` closes that gap for the domain-tree fleet: the first occurrence of a novel failure pays for one bounded, read-only Claude call; every subsequent occurrence of the same signature is handled deterministically by the persisted, validated node the call produced, with no further LLM cost or latency.

**Guardrails:** strict vocabulary validation (the proposal must resolve entirely to registered action/condition names, `internal/engine/registry.go`); a 5-extension cap per handler (`internal/engine/error_handler_claude.go`), after which Claude is no longer consulted and failures pass through unchanged; auto-disable of an individual extension after 3 consecutive failures (`errorHandlerDisableAfter`, `internal/engine/error_handler_store.go`); and a `BT_CLAUDE_ERROR_HANDLER=off` kill switch (`internal/engine/error_handler_claude.go`) that makes the decorator a transparent passthrough. The decorator is also a no-op passthrough under gardener sandbox scoring (`bb.Sandbox`), since structural fitness evaluation must never call Claude or touch the store.

**Where:** `internal/engine/error_handler_node.go` (`BuildClaudeErrorHandler`, wired into `buildNode` at `internal/engine/tree.go:348`), `internal/engine/error_handler_store.go` (persisted extension ledger, consecutive-failure disable), `internal/engine/error_handler_claude.go` (cooldown, extension cap, kill switch, strict-vocabulary Claude proposal call); every `AllDomainTrees()` root is wrapped via `wrapWithErrorHandler` (`internal/domains/trees.go`). Pinned by `TestClaudeErrorHandler_ProposalGraftedAndTicked`, `TestClaudeErrorHandler_GraftedExtensionHandlesNextRunWithoutClaude`, `TestClaudeErrorHandler_UnresolvableStampsCooldownAndPassesFailureThrough`, `TestClaudeErrorHandler_KillSwitch`, and `TestClaudeErrorHandler_CapReachedSkipsClaude` (`internal/engine/error_handler_node_test.go`), and `TestErrorHandlerStore_ConsecutiveFailuresDisable` (`internal/engine/error_handler_store_test.go`).

**Effect:** A recurring subtree failure is fixed once and handled deterministically thereafter, without unbounded LLM spend, an unbounded extension surface, or a single misbehaving extension silently wedging a handler — and the whole mechanism disappears cleanly under sandbox scoring or the kill switch.

## 8.17 Composable Blocks and Expand-at-Build

**What:** Reusable subtree blocks are composed into task trees and expanded at build time (→ ADR-131). Block IDs (`core:plan`, `core:tools_dev`, …) are registered in `internal/blocks` and referenced as `SubTreeRef` nodes; the engine expands them before `buildNode` runs, so reliability decorators (Timeout, CircuitBreaker) and actions execute correctly in the fully expanded tree.

**Why:** Composing trees from named, reusable blocks lets one validated implementation of a stage (planning, tool setup, error handling, HITL approval) serve every tree that references it, instead of each tree duplicating the subtree inline.

**Where:** `internal/blocks` (block registry, `blocks.Expand`), `internal/engine/tree_expand.go` (`RegisterTreeExpander`); the block/preset inventory, persistence location, and managing `bt_blocks_*` MCP tool family are in [§5.0](05-building-blocks.md).

**Effect:** HITL blocks integrate with `internal/hitl` and the dashboard approve/reject APIs; evolution can mutate block refs (`FilterEvolutionMutations`, [§5.0](05-building-blocks.md)); and composition at the operator boundary is validation-gated (§8.15).
