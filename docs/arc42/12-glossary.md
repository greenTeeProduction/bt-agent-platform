# 12. Glossary

The most important domain and technical terms, defined once — the canonical
meaning used across all sections. Sorted alphabetically.

| Term | Definition |
|---|---|
| **A2A** | Agent-to-Agent protocol. Enables agents to discover each other via agent cards and delegate tasks. Runs on HTTP :8686. |
| **Action** | A leaf node in a behavior tree that performs a side-effecting operation (read file, call LLM, write output). Returns Success (1) or Failure (0). |
| **ADR** | Architecture Decision Record. Documents a significant design choice with context, decision, and consequences. Immutable once accepted. |
| **Agent Card Signing** | An unkeyed SHA-256 content-hash integrity check over an `a2a.AgentCard` (`SignAgentCard`/`VerifyAgentCard`, `internal/a2a/signing.go`) — detects tampering or staleness, not origin (any party can compute a valid hash over their own forged card). Since 2026-07-14 (ADR-090), both card-producing paths sign: `ConvertToAgentCard` (`internal/a2a/card.go`, the origin point every registered-agent card passes through) and `handleGlobalAgentCard`'s ad hoc `/.well-known/agent-card.json` response (`internal/a2a/server.go`). `auctionCandidates` (`internal/a2a/auction.go`) — the trust boundary turning the live card registry into `AuctionDelegate`'s dispatchable candidates — checks it via `cardSignatureValid`: an unsigned card is trusted (signing is opt-in), but a card whose trailing signature no longer verifies against its content is excluded before `EligibleBidders` ever sees it. |
| **Auction (Contract Net)** | A2A task-allocation protocol: an Auctioneer announces a task, candidate agents bid from their agent-card capabilities, and the lowest-cost eligible bid is awarded and dispatched the work. `Auctioneer.RunAuction`, `internal/a2a/auction.go`. Since 2026-07-13 (ADR-064), winner dispatch is honest (`SendTask` returns a real error for any non-success outcome instead of formatting it as a success string) and resilient (bounded retry, then a per-winner `reliability.CircuitBreaker`, threshold 3/cooldown 30s). Since 2026-07-13 (ADR-065), production dispatches through `NewPersistentAuctioneer`, so that breaker survives across engine ticks (not just repeated calls on one `Auctioneer` instance, which production never made) and across restarts, round-tripped through `circuit_breakers.json`. |
| **Award** | The auction outcome naming the winning bidder and its winning Bid for an announced task. Produced by ScoreEvaluator. |
| **Bid** | A candidate agent's offer to perform an announced task, carrying cost and confidence scored from its agent card via ScoreAnnouncement. Returned by the bid-aware A2A responder. |
| **Blackboard** | Shared state object passed through behavior tree ticks. Carries Task, Plan, Result, Outcome, ChainState, ChainTools, Reflections, TreeStore. `engine.Blackboard` itself carries no synchronization (`internal/engine/tree.go:107`); in `cmd/bt-agent`, `mcpDeps` holds the single production instance shared across concurrent MCP tool calls. Since 2026-07-16 (ADR-123, milestone 1/5), `mcpDeps.bbMu` guards `bt_run_task`'s full Task-assign → RunTask → response-read critical section against concurrent callers. Since 2026-07-16 (ADR-123, milestone 4/5), `bt_blocks_compose(save:true)` (`blocks_tools.go`), `bt_hitl_compose_task(save:true)` (`hitl_tools.go`), and `injectPersonaContext` (`persona_tools.go`, via a self-locking wrapper over the reentrant-unsafe `injectPersonaContextLocked` body `bt_run_task` calls directly) are guarded too; `bt_delegate_to_tree` and the `bt_use_*_tree` switchers (all in `tools.go`) are the only remaining unguarded handlers. Since 2026-07-16 (ADR-123, milestone 5/5), `engine.Server` itself (not `mcpDeps`) gained an analogous `bbMu sync.Mutex` plus a `RegisterBlackboardTool` method that locks around any handler registered through it — a registration-time guarantee rather than an ad hoc per-handler call — proven race-free under `-race` by a dedicated `Server.Run()`-driven test. Since 2026-07-16 (ADR-124), `cmd/bt-agent` migrated `bt_delegate_to_tree`, all four `bt_use_*_tree` switchers, `bt_run_task`, `bt_blocks_compose`, and `bt_hitl_compose_task` onto `RegisterBlackboardTool` and deleted `mcpDeps.bbMu`/`lockBB`/`unlockBB` outright, so `engine.Server.bbMu` is now the single shared-blackboard lock guarding every one of them. |
| **Build Identity** | The VCS identity a binary was built from (revision, commit time, dirty flag), read via `runtime/debug.ReadBuildInfo`. Logged at startup by bt-agent and bt-gardener and exposed as the single-series `bt_build_info{revision,dirty}` gauge on the metrics exposition; unstamped builds report an `unknown` sentinel instead of an empty label. Stale-daemon-binary drift is detected by comparing this revision against repo HEAD — automated via `DriftStatus` (ADR-044) on a 20-minute background cadence and at every scheduler cycle, and stamped as `build_revision` onto dead letters and webhook events. ADR-023, ADR-044. |
| **BuildTree** | Converts a SerializableNode tree definition into a runnable go-bt Command tree. Validates structure before building. |
| **Chain Type** | One of the LLM workflow patterns wrapped by ChainAction (inventory in [§5.5](05-building-blocks.md)). Validated against the declared `ChainKind` constants at authoring time by `IsKnownChainKind` (`internal/engine/chains.go`, ADR-130). |
| **ChainAction** | A behavior tree leaf node that wraps an LLM call (chain-type inventory in [§5.5](05-building-blocks.md)). Reads config from node Name and Metadata. Since 2026-07-16 (ADR-130), a leaf-children declaration and an unrecognized `chain_type` both fail validation at authoring time (`IsKnownChainKind`, §8.2, §8.13) instead of only at tick time. |
| **Circuit Breaker** | 3-state pattern (closed/open/half-open) that prevents cascading failures. Per-agent isolation via AgentCircuitBreakerStore, now durable: `Save`/`Load` (`internal/agent/scheduler_cb.go`) persist and restore state through `circuit_breakers.json`, written on every `runJob` outcome and restored on `NewScheduler` — the file the dashboard's `cb_status` column has always read but that, before ADR-063 (2026-07-13), no writer ever populated. Since 2026-07-13 (ADR-054), `ACPClient` also carries its own `reliability.CircuitBreaker` keyed by ACP command, tripped by repeated subprocess-start/session-setup failures so a crash-looping ACP subprocess is not respawned on every `GenerateCtx` call. Since 2026-07-13 (ADR-064), `Auctioneer` carries a third, independent population — one `reliability.CircuitBreaker` per auction winner name, threshold 3/cooldown 30s. Since 2026-07-13 (ADR-065), production's `NewPersistentAuctioneer` routes that population through a process-wide `winnerBreakerStore` that also persists to `circuit_breakers.json`, namespaced under an `"a2a.auction.winner."` key prefix so it coexists with the scheduler's per-agent entries in the same file without a shared Go type; `NewAuctioneer` (ad hoc/test callers) keeps the original in-memory-only, per-instance map. Since 2026-07-13 (ADR-074), a fourth, package-level breaker (`embeddingBreaker`, `internal/knowledge/embeddings.go`) guards `EmbeddingClient.GetEmbedding`'s Ollama HTTP call — threshold 3/cooldown 60s, shared across every `EmbeddingClient` instance rather than per-instance — so a dead embeddings backend is timed out (a paired 2s `http.Client` timeout) and then skipped entirely instead of being re-dialed and re-timed-out on every subsequent `BuildIndex`/`discoverWithEmbeddings` call. |
| **Claude Backoff** | Durable rate-limit window for the GOAP fusion loop: a rate-limited Claude outcome persists an RFC3339 `goap_fusion_claude_backoff_until` deadline (agent-scope blackboard, ChainState fallback); while active, both Claude consumers skip in milliseconds — the plan-resume runtime degrades to ScheduledAnalysisPath preserving its carryover, the review fallback returns rate-limited without invoking Claude. Half-open: an elapsed or malformed deadline reads as inactive. `BT_GOAP_CLAUDE_BACKOFF` (default 6h) on the implementation path, fixed 1h on the review path. ADR-016. |
| **CMA-ES** | Covariance Matrix Adaptation Evolution Strategy (`internal/evolution/cmaes.go`): continuous optimization of node-level numeric parameters (timeouts, retry counts, thresholds) rather than tree topology. `TuneTreeParameters` is the production seam — Extract→Optimize→Apply on clones, never mutating the input; reached via `bt_evolve_bottlenecks`, which routes parameterized trees to CMA-ES and parameterless ones to genetic evolution (ADR-020). |
| **Condition** | A leaf node that evaluates a boolean predicate. Used in PreGate and OutcomeSelector for branching decisions. |
| **Crisis Detector** | Proactive population-health monitor (`internal/evolution/crisis_detector.go`), the counterpart to the reactive QualityGate. `DetectPopulation` flags `diversity_collapse`/`regression_spiral`/`quality_crash`; on a hit, the shared `Population.selfHealGeneration` envelope overrides the generation's mutation rate with the emergency rate (μ_emergency = 0.50) and resets streak counters after a spiral. Reachable in production via `bt_evolve_qd` (`EvolveMAPElites` since 2026-07-15, ADR-110 — previously plain `Evolve`), via `bt_evolve_genetic`/`bt_evolve_bottlenecks`/`bt_evolve_selection_pressure`'s live-bank `EvolveWithExperience` path (ADR-038 milestone 2), via `bt_evolve_island`'s per-island `EvolveAll` (ADR-038 milestone 5), via `bt_evolve_multiobjective`'s `NSGAIIPopulation.Evolve` (ADR-051), and, since 2026-07-15 (ADR-121), via `bt_evolve_qlearning`'s `EvolveQLearning` and `bt_evolve_memetic`'s `MemeticEvolve` too (`ParetoPopulation.EvolvePareto` — ADR-038 milestone 4 — runs it but has no `bt_evolve_*` caller yet). Its `SpecialistRegistry` companion preserves the best validated `specialist:<type>` archetype for crisis resurrection; the observe→resurrect loop runs wherever `selfHealGeneration` does — including the MAP-Elites illuminator `EvolveMAPElites`, which since ADR-121 delegates to the shared method directly rather than its own ADR-031-milestone-5 copy of the same logic — live in prod since `newProductionPopulation` (`cmd/bt-agent/tools.go`) seeds every MCP-tool population's registry via `SeedSpecialistRegistry`. Self-healing signals are exported as one read-only value via `Population.HealthSnapshot()` (`PopulationHealth`: crisis reasons, applied mutation rate, generation, resurrection count — ADR-032). Separately, `Gardener.evolveTreeV2` (`internal/gardener/evolve_v2.go`) holds its own `CrisisDetector` instance on `gardener.Config.CrisisDetector` for its per-cycle "Stage 3.5" check — unrelated to the GA `Population.Crisis` field above — and, since 2026-07-15 (ADR-102), scales that cycle's mutation budget from the detector's own `EmergencyRate` (`ceil(MaxMutations / (1 - rate))`) instead of a hardcoded `× 2`; production still constructs it via the unchanged 0.50 default. ADR-031, ADR-038, ADR-102. |
| **Dead Letter Queue (DLQ)** | Persistent JSON file (`dead_letter_queue.json`) that stores tasks whose retries have been exhausted. Bounded at `MaxDeadLetterEntries` (1000) with oldest-first eviction. The dashboard flags an entry for retry via `Requeue` (stamps `RequeuedAt`, keeps the entry on disk) rather than destructively replaying it cross-process; an entry whose replay `Attempts` reach `MaxReplayAttempts` (5) is terminally flagged `Abandoned` and excluded from further auto-requeue. The file is multi-writer (daemon, dashboard, MCP siblings): saves are atomic (tmp+rename) and re-merge on-disk entries under a `<path>.lock` sidecar flock so sibling requeue stamps survive; a corrupt file is quarantined to `<path>.corrupt` instead of silently restarting (and re-persisting) an empty queue; and every cross-process consumer — the daemon's replay scan, `bt_dlq_replay`, `bt_dlq_list`, the dashboard DLQ panel — calls `Reload()` before consuming; `Push` also defaults an empty `ID` (agent name + nanosecond timestamp + a push counter) so callers that never set one, like the HITL-exhausted escalation path, don't collide and cross-contaminate each other's replay state under the ID-keyed merge. ADR-025, ADR-036, ADR-047. |
| **DefaultTree** | The fallback behavior tree used when no specific tree matches. Extracted from a 750-line god node into 21 paths across 7 category files. |
| **Deferred Outcome** | A graceful, expected scheduler pause (e.g. the `goap_fusion_rate_limited` Claude rate-limit carryover) recorded via `SLOMetrics.RecordDeferred` into a dedicated `DeferredCalls` counter. It is terminal — neither retried nor dead-lettered — and deliberately leaves the success/failure counters and latency totals untouched so a backoff never inflates the success rate or success-latency the gardener's validation gate reads. Reaching `RecordDeferred` at all depends on `engine.RunTask`'s terminal switch preserving the sentinel rather than collapsing it to a raw success/failure code first — not actually guaranteed until ADR-120 (2026-07-15). ADR-025, ADR-120. |
| **Deploy Drift** | The condition where a long-running daemon (bt-agent, bt-dashboard, bt-gardener) serves code older than repo HEAD after an autonomous landing. Diagnosed by `DriftStatus` (`internal/agent/deploy_drift.go`), which shells `git rev-parse HEAD` and compares it to the running Build Identity; an unstamped revision is never reported stale. Detection-only by default (`StartDriftWatcher`, every scheduler cycle); out-of-place rebuild+swap (`rebuild.go`, `RebuildBinaries`) is opt-in via `BT_AUTO_REBUILD_ON_DRIFT` and does not itself restart the process. Each of the three mains passes its own `RebuildTarget` list — `bt-dashboard` uses `DashboardRebuildTargets`, which (unlike `DefaultRebuildTargets`) includes bt-dashboard's own binary (ADR-045), so its watcher can actually adopt a fix rather than only rebuilding its siblings. A `RebuildBackoff` guard and `Scheduler.AnyInFlight()` throttle retry-storms and avoid swapping mid-job (ADR-045); both are now wired into production (ADR-050) — all three mains set `Backoff: agent.NewRebuildBackoff()`, and `bt-agent` additionally sets `InFlightFn: globalSched.AnyInFlight` since it is the only one of the three that owns a live `Scheduler` (`bt-dashboard`/`bt-gardener` have no equivalent guard). Program 94b0b31, ADR-044, ADR-045, ADR-050, R13. |
| **Evolution Lineage** | The base-tree ↔ evolved-descendant relationship recorded as `evolved_from` `Relations` edges by `RegisterEvolved` and resolved by `KnowledgeGraph.EvolutionLineage(treeID)` (`baseID`, `evolvedIDs`, `ok`). Since 2026-07-16 (ADR-126), exposed per-tree in the `/api/trees` response as a `lineage` object. Since 2026-07-16 (ADR-127), also consulted before spending another evolution budget: `EvolutionLineageBestFitness(treeID)` returns the highest `StructuralFitness` among `treeID`'s evolved descendants, and `bt_evolve_bottlenecks` skips re-evolving a bottleneck whose lineage already has a fitter descendant backed by a non-regressing shared `TrackRecord` (`WinRate() >= 0.5`). |
| **Evolution** | The process of systematically improving behavior trees through mutation, fitness evaluation, and selection. Six algorithms available ([§1.1](01-introduction-goals.md)). |
| **Experience Bank** | Persistent store of successful mutation experiences (`~/.go-bt-evolve/experience/experience.json`), EvoRepair-inspired. Warm-starts `EvolveWithExperience` operator selection via tree-type retrieval; only fitness-improving mutations are recorded. Wired into `bt_evolve_genetic` and `bt_evolve_bottlenecks` (ADR-017) and shared with bt-gardener, whose v2 cycles record accepted mutations and bias candidate ordering from the same file (ADR-021). Bounded at 500 entries: quality-aware eviction (lowest quality/oldest first, `TimesReused >= 3` protected) enforced on Add and on load (ADR-018). Safe for the two concurrent writers: every full-file write path (Add, MarkReused, Persist) re-merges on-disk entries by ID and holds an exclusive flock on the `experience.json.lock` sidecar across merge→rename (ADR-022, ADR-024). Since 2026-07-13 (ADR-062), `TransferExperiences(sourceTree, _)` genuinely reads `sourceTree`'s own entries (`RetrieveByTreeType`) and `SeedDomain(sourceTree, targetTree)` copies up to 5 of them into `targetTree`'s pool, re-tagged as native — the mechanism an optional `IslandModel.Bank` field uses to make `Migrate` seed a migration target domain's experience pool from its source, though no production `bt_evolve_island` call wires `.Bank` yet. Since 2026-07-15 (ADR-109), warm-starting is no longer tree-type-only: `Population.EvolveWithExperienceContext` (which `EvolveWithExperience` now wraps) warm-starts from `Retrieve(query, ...)` instead of `RetrieveByTreeType` whenever a caller supplies a non-empty query, and `bt_evolve_bottlenecks`' genetic path queries with the bottleneck's own `LastFailureTask` — `AddFromMutation` also gained an optional `failureContext` parameter to record that same task text into a new entry's `Context`. Since 2026-07-16 (ADR-125), the genetic-algorithm and gardener recorders both supply it too: `Population.mutateAndRecord` passes `EvolveWithExperienceContext`'s own `query`, and `evolveTreeV2`'s two `AddFromMutation` call sites pass a new `lastFailureTask(records)` helper's result (the tree's most recent `evolution.Failure` reflection record's `Task` text) — and the gardener's `biasCandidatesWithExperience` retrieval is conditioned on that same signal, routing through `Retrieve(query, ...)` when non-empty instead of the tree-type-only `RetrieveExperienceHints`. |
| **Expert Knowledge** | Curated design patterns (6) and anti-patterns (5) that guide tree evolution. Includes TreeArchetypes for each category. Since 2026-07-15 (ADR-095), `ExpertKnowledge` also carries a durable `LearnedPatterns` archive alongside this hardcoded catalog: `Observe(action, category, gain)` (nil-safe, non-positive gains discarded) records genuinely fitness-improving mutations, `Population.EvolveQLearning`/`qLearnMutate` (`internal/evolution/learning.go`) call it for every mutation via an optional `ek *ExpertKnowledge` parameter, and `Save`/`Load` persist it as JSON to `~/.go-bt-evolve/expert_archive-<tree>.json` — one file per sanitized base tree, mirroring `QTable.Save`/`Load` (ADR-041). `bt_evolve_qlearning` warm-starts and re-persists it every call; `bt_evolve_expert` warm-starts from the same file before `RecommendMutations`/`DetectAntiPatterns` and returns the merged `learned_patterns` alongside the hardcoded catalog's recommendations, so advisory calls surface cross-run learning instead of only the static benchmark-derived rules. Since 2026-07-15 (ADR-103), `Observe` also caps `LearnedPatterns` at 500 entries (`learnedPatternCap`), evicting the lowest-`Gain` entry on overflow — mirroring the Experience Bank's ADR-018 cap-500 pattern — closing the one durable evolution-package archive that previously had no `Cap` analogue. Since 2026-07-15 (ADR-104), the underlying `Observe` call is also wired into `ParetoPopulation.EvolvePareto`, `NSGAIIPopulation.Evolve`, `IslandModel.EvolveAll`, and `MAPElitesPopulation.EvolveMAPElites` via their own optional `ExpertKnowledge` fields; since 2026-07-15 (ADR-106), `bt_evolve_multiobjective`, `bt_evolve_pareto`, and `bt_evolve_island` (`cmd/bt-agent/tools.go`) now construct, warm-start, and persist that field with the same `expertArchivePath`-scoped Load/Save sequence `bt_evolve_qlearning` established; since 2026-07-15 (ADR-110), `bt_evolve_qd` does too — it now constructs a `MAPElitesPopulation` and drives `EvolveMAPElites` directly instead of a bare `Population.Evolve` — so all five production tools populate the durable archive today. |
| **Fitness Score** | Multi-dimensional evaluation of a behavior tree's performance. Dimensions include correctness, completeness, conciseness, actionability. |
| **Gardener** | The evolution orchestrator (`cmd/bt-gardener`). Runs evolution cycles: evaluate → order mutations (experience-biased, ADR-021) → apply → re-evaluate → accept (recorded to the shared Experience Bank) or rollback. Each cycle's outcome is a `CycleMetrics` record (a `crisis_intervention`/`CrisisIntervened` flag pair and a `MutationBudget` int when the cycle-level crisis detector boosted the mutation budget), persisted to `~/.go-bt-gardener/gardener-metrics.json` as an aggregate document — `last_run`, `total_crisis_interventions`, and, since 2026-07-13, `total_cycles`/`active_trees`/`best_fitness`/`total_improvements` too, alongside the full history — that the dashboard's gardener panel parses (ADR-032). Since 2026-07-15 (ADR-114 milestone 3), the same document also aggregates `total_deep_search_cycles`/`avg_tt_hit_rate` from each cycle's `DeepSearchUsed`/`TTHitRate` fields (Transposition Table entry, below); no dashboard consumer reads these two yet. Since 2026-07-15 (ADR-115 milestone 3), it also aggregates `total_rollbacks` from each cycle's `CycleMetrics.Rollbacks` — unlike the deep-search pair above, the dashboard's `GardenerMetrics.Rollbacks` field (`internal/dashboard/metrics.go`) does read it, so a rollback cycle is visible on the gardener panel. `evolveTreeV2`'s fail-closed path — reached once its `QualityGate` reports a tree's consecutive failures over threshold — now triggers `Registry.RollbackTree` automatically the moment the gate disables, rather than only pausing mutations for that tree (ADR-115 milestone 2), and its pre-mutation `SnapshotTree`/`RestoreTree` calls (Pre-Mutation Snapshot entry, below) keep multi-revision history instead of one file overwritten each cycle (ADR-115 milestone 1). `evolveTreeV2`'s per-tree loop skips any registry entry with `Active=false`; since 2026-07-15 (ADR-098), a `gardener_deactivate_all` langchain tool calls `Registry.DeactivateAll()` to flip every entry inactive at once — an operator-triggered kill switch, live-process-only since `Active` is never persisted and resets to `true` on the next restart. |
| **GOAP Fusion Loop** | The scheduled self-improvement cycle (`domain:goap_fusion_loop`, cron 0,30): research → goals → plan → implement → verify → land, wired with Phase-0 preflight, circuit gates, and state-hash producers. |
| **GOAP** | Goal-Oriented Action Planning. PlannerNode extends UtilitySelector with goal management, world state, and available actions. |
| **Grill** | Multi-turn critical NotebookLM review ("what is the framework missing?") rotating rounds 1-3 across cycles; answers feed the shared goal list. Round questions are served from the per-day query cache. |
| **HITL** | Human-in-the-loop approval gate node (HumanApprovalGate). Requests persist under `~/.go-bt-evolve/hitl/`; policy can auto-approve. A gate's `side_effect_class` metadata (`"destroy"`/`"external"` vs `"local_reversible"`) decides whether it can ever bypass a live human at all — `"destroy"`/`"external"` forces the mandatory-human path regardless of policy, while `"local_reversible"` combined with `auto_approve: true` lets an unattended scheduled cycle self-resolve the gate in-tick. `GoapFusionTree`'s `ApproveGoapFusionApply` set this shape from the start; `BTFusionTree`'s `ApproveFusionReportWrite` was misclassified `"external"` with no `auto_approve` and deadlocked every unattended `bt_fusion` cycle on a `pending_approval` outcome no human was present to resolve, fixed by matching `ApproveGoapFusionApply`'s classification (2026-07-16, ADR-122, milestone 1/2). Since ADR-056, an escalated request (`StatusEscalated`, set by `Store.Escalate` via `POST /api/hitl/<id>/escalate`) is resolvable: `Store.Approve`/`Store.Reject` accept it as a valid pre-state alongside `StatusPending`, and `Store.WaitForRequest` terminates on it immediately instead of polling until context cancellation. Since ADR-061, the dashboard workflow path treats that termination correctly rather than as an implicit approval: `WorkflowApprovalWait` sets `Approved = true` only for `StatusApproved`/`StatusSkipped` (a distinct `Escalated bool` covers `StatusEscalated`), `executeStep` gives an escalated approval step its own `"escalated"` outcome that halts the pipeline like a rejection, and `FindPendingByTaskID` (backing `ApproveByTaskID`/`RejectByTaskID`) matches `StatusEscalated` alongside `StatusPending` so an escalation is resolvable by task ID too. Since ADR-068, the by-task-ID REST (`handleTaskApprove`/`handleTaskReject`) and MCP (`bt_workflow_approve`) resolution paths also report which case actually happened — `hitl_resolved_from`/`resolved_from` is `"escalated"` vs `"pending"`, and a task with no matching request surfaces the underlying error as `hitl_note` instead of resolving silently — closing the 4-milestone HITL-escalation program. Since 2026-07-13 (ADR-077), a gate's `bb.Outcome = "pending_approval"` is preserved as a non-terminal outcome all the way through `engine.RunTask` (instead of collapsing to `"partial"` at the tick limit) and through the A2A responder, where `TaskStateBridge.BTToA2A` maps it to `a2a.TaskStateInputRequired` so an A2A caller sees the task as awaiting input rather than failed. |
| **Impact Graph** | Change-impact analysis mapping each source file to the tests a change to it can affect, via import-based edges and directory proximity (`BuildImpactGraph`/`ImpactGraph.TestsFor`, `internal/knowledge/impact.go`). `ImpactedTests(root, source)` is the single build+query entry point; since ADR-052 it has two production consumers — the `bt-agent-cli impact <source-file>` subcommand and the `bt_impact_tests` MCP tool — neither yet wired into `make check-quick` or the pre-commit hook. Both consumers normalize their input path via `NormalizeImpactSource(root, source)` and return an explicit error for a path outside `root` rather than a silent empty test list (ADR-070/ADR-071). |
| **Island Model** | An evolution algorithm where sub-populations evolve in isolation with periodic migration of top individuals. Reachable in production via the deterministic `bt_evolve_island` MCP tool; its optional `domains` parameter seeds one island per registered domain tree, matching the type's stated purpose of maintaining genetic diversity across domains. Durable as of ADR-033: `Save`/`Load` persist per-domain subpopulations (genome-deduped, fitter-copy-wins merge) to `~/.go-bt-evolve/island_archive-<tree>.json` — one archive per sanitized base-tree ID (ADR-034) — which the tool warm-starts from and re-persists on each call. Evolved-fitness write-back follows seeding (ADR-035): in domains mode each seeded `domain:<name>` entry is credited with its own island's best elite; in default mode the base tree alone receives the cross-island best. Since ADR-038 milestone 5, `EvolveAll` runs each island's generation through the shared `Population.selfHealGeneration` envelope (seeding `Specialists`/`Crisis` for islands that lack them) instead of a bare `Evaluate`, so a collapsing island resurrects an extinct specialist archetype before its elites migrate; per-island `Resurrections` aggregate into `IslandStats.Resurrections`, though `bt_evolve_island`'s JSON response does not yet surface it. Bounded as of ADR-040: `Cap` (per-island individuals) and `IslandCap` (distinct island keys) are enforced on every `Load`, evicting lowest-fitness individuals and lowest-`BestFitness` adopted islands respectively; `bt_evolve_island`'s `population_cap`/`island_cap` parameters set them before `Load`, defaulting to 3x the call's own population/island counts when omitted. Since ADR-062, an optional `Bank *ExperienceBank` field makes `Migrate` call `Bank.SeedDomain(srcDomain, tgtDomain)` for every domain pair that actually migrated an individual, transferring the source domain's own experience entries into the target's pool — implemented and tested, but `bt_evolve_island` does not yet set `.Bank`. Since 2026-07-15 (ADR-096, milestone 2/4), `bt_evolve_island`'s durable-archive save is gated: the handler now captures `EvolveAll`'s per-domain best-tree map (previously discarded), picks the seeded domain with the highest structural fitness as the cross-island winner, and runs it and the base tree through `benchmarkGateEvolvedWinner` immediately before `im.Save` — a winner that regresses on the tree's real `internal/benchmark` suite skips the save, reporting `benchmark_gate_rejected` rather than trusting `StructuralMultiFitness` alone. |
| **Knowledge Graph** | In-memory graph of all registered trees with capabilities, keywords, embeddings, and cross-tree relationships. Powers discovery and auto-creation.
